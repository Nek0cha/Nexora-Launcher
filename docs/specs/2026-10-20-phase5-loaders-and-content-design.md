# フェーズ 5：ローダーの導入と MOD の管理の設計

- 作成日：2026-10-20
- 状態：承認済み（2026-10-20）
- 前提：`docs/specs/2026-10-15-nexora-architecture-design.md`（spec 0）の 4、5、13 節、`docs/specs/2026-10-19-phase4-instance-ui-design.md`（spec 4）、`docs/specs/2026-10-19-phase4-polish-design.md`
- 根拠：`docs/research/02-mod-loaders.md`（ローダーの導入）、`docs/research/04-content-providers.md`（Modrinth の API）

## 1. 目的と範囲

フェーズ 5 の終了時点で、ユーザーが次のことをランチャーの中だけでできる状態にする。

1. インスタンスを作るときに、Vanilla、Fabric、Forge、NeoForge、Quilt のいずれかを選べる。
2. インスタンスに入っている MOD を一覧し、有効と無効を切り替え、jar のドラッグ＆ドロップで追加し、削除できる。
3. Modrinth で MOD を探し、必須の依存 MOD と一緒にインスタンスへ導入できる。
4. 導入済みの MOD に更新があるかを知り、1 件ずつ、またはまとめて更新できる。

### 1.1 背景

spec 0 の 13 節では、フェーズ 5 を「Fabric、Quilt、Modrinth 連携」、フェーズ 7 を「Forge、NeoForge、`.mrpack`」としていた。ユーザーの普段の遊び方は Fabric と Forge が中心であり、Forge で試せない MOD 管理は価値が薄い。このため、Forge と NeoForge の導入をフェーズ 7 からこのフェーズに前倒しする（2026-10-20 にユーザーが承認）。`.mrpack` のインポートとエクスポートはフェーズ 7 に残す。

### 1.2 実装の分割

規模が大きいため、実装計画と PR は次の 4 つに分ける。この順に進め、各段階で実機の動作確認を行う。

| 段階 | 内容 |
|---|---|
| 5-1 | Fabric と Quilt の導入、インスタンス作成ダイアログの拡張（3 節） |
| 5-2a | Forge（1.13 以降）と NeoForge の導入（4.1、4.2 節） |
| 5-2b | 旧形式の Forge（1.8.9〜1.12.2）の導入（4.3 節） |
| 5-3 | インスタンスの「コンテンツ」タブ（MOD の一覧、切り替え、追加、削除）（5 節） |
| 5-4 | Modrinth との連携（検索、依存の導入、更新）（6 節） |

### 1.3 目標でないこと（範囲外）

| 項目 | 扱い |
|---|---|
| リソースパック、シェーダー、データパックの管理 | 後のフェーズ。`instance_contents.kind` は将来に備えてそのまま残し、このフェーズで書き込む値は `mod` のみとする（builder の判断ではなく、ここで決める） |
| `.mrpack` のインポートとエクスポート | フェーズ 7 |
| CurseForge | フェーズ 10 |
| スクリーンショットのタブ、ログのタブ、スキン専用の画面 | 後のフェーズ |
| MOD の設定ファイルの同期 | フェーズ 6 |
| メモリの自動設定（`memory_mode = auto` の算出） | フェーズ 9 |
| 作成済みのインスタンスのローダーの追加と変更。導入に失敗したときは、`broken` からの再試行でローダーの導入をやり直せればよい | 必要になった時点 |

### 1.4 してはいけないこと

- 起動中のインスタンスの `mods/` を変更しない（切り替え、追加、削除、更新のすべて）。拒否の理由は画面に出せるエラーとして返す。spec 4 の複製と削除の方針に合わせる。
- 更新の途中で失敗したとき、MOD を失った状態や、古い版と新しい版が両方入った状態で終わらせない（6.5 節）。
- ユーザーが置いた jar を、確認なしに削除や書き換えをしない。Modrinth で特定できない jar は、そのまま「ローカル」として一覧に残す。

## 2. 全体の構成

- 新しい処理は `nexora-core` に置き、UI は既存の IPC の入口（Tauri コマンドとイベント）から呼ぶ。spec 0 の層の分け方に従う。
- ローダーの導入は、spec 0 の 5.1 節の第 4 段階（loader）として、既存の「解決」「計画」「取得」「起動」の流れに接続する。ローダーのプロファイルは `shared/` に固定して保存し、オフラインの起動は `shared/` だけで行える。
- 長い処理（ローダーの導入、MOD のダウンロード、更新）は、既存のタスク管理（`task/`）に載せる。タイトルバーのタスクボタンで進捗を見られる。
- Modrinth への通信は、既存の HTTP クライアントとダウンロード処理（`net/`）を使う。`User-Agent` に、アプリ名、バージョン、連絡先を入れる（調査 4 の形式）。

## 3. 5-1：Fabric と Quilt、作成ダイアログ

### 3.1 ローダーの導入

- spec 0 の 5.3 節のとおり、公式のプロファイル JSON を Vanilla に重ねる（`inheritsFrom`）。取得元は meta.fabricmc.net（v2）と meta.quiltmc.org（v3）である。
- 対応範囲は、各ローダーの公式メタデータ（Fabric の `/v2/versions/game`、Quilt の `/v3/versions/game`）が対応するとして示す Minecraft のバージョンとする。作成ダイアログで「ローダーに合わせて Minecraft のバージョンを絞る」のも、この一覧から導く。spec 0 の 5.3 節にある「1.8.9 以降」は、Fabric と Quilt の実際の対応範囲（1.14 以降）と合わないため、この記述に置き換える（調査 2 の表と一致する）。
- インスタンスには `loader` と `loader_version` を保存する（列は既にある）。`loader_version` が空の場合は作らない。作成時に「最新の安定版」を解決して保存する。
- 導入が終わるまで `state` は `installing` とし、失敗したときは既存の Vanilla の失敗と同じ扱い（`broken`、再試行できる）にする。
- 起動時は、保存済みのローダーのプロファイルを `shared/` から読む。ローダーを Vanilla に重ねたプロファイルの解決、ライブラリの取得、`mainClass` の差し替えは、既存の解決と計画の段階を拡張して行う。

### 3.2 作成ダイアログ

既存の `CreateInstanceDialog` を拡張する。見た目は小さいダイアログのままとし、詳細設定は展開式にする（モックアップの案 A、2026-10-20 にユーザーが選択）。

| 部分 | 内容 |
|---|---|
| ローダーのタブ | Vanilla / Fabric / Forge / NeoForge / Quilt の 5 つ。既定は Vanilla |
| 基本の欄 | 名前、Minecraft のバージョン、ローダーのバージョン（Vanilla のときは出さない） |
| 詳細設定（展開式、既定は閉じる） | メモリ、Java、JVM 引数。既存の編集画面（spec 4）と同じ値と同じ検証を使う。解像度は 3.3 節で扱う |

- ローダーのバージョンの既定は「最新の安定版」とし、選び直せる。
- ローダーのタブは、そのローダーが対応するバージョンが、ダイアログの知る正式版の中に 1 つでもあれば選べる。1 つも無い場合だけ、選べない状態にして理由を示す（例：「対応するバージョンがありません」）。選んだタブが今の Minecraft のバージョンに対応していなければ、バージョンをそのローダーが対応する最新のものへ移す。ローダーを先に選んだ場合は、Minecraft のバージョンの選択肢をそのローダーが対応するものに絞る。
- Forge と NeoForge のタブは、5-2a が終わるまで選べない状態にする（理由は「準備中」と示す）。旧形式の Forge（1.8.9〜1.12.2）は 5-2b が終わるまで選べない。
- 詳細設定を閉じたままでも作成できる。値を変えていなければ、従来と同じ既定値で作る。
- 名前の既定値は、従来の Minecraft のバージョン名に、ローダー名を足した形にする（例：`Fabric 1.21.4`）。ユーザーが名前を編集した後は、バージョンやローダーを切り替えても書き換えない（既存の `nextName` の方針を引き継ぐ）。具体的な形式は builder が決める。

### 3.3 解像度（未決を builder の判断とする）

ユーザーが挙げた詳細設定の項目に解像度があるが、`instances` テーブルに対応する列がない。このフェーズでは、解像度を詳細設定に含めるかを builder が判断してよい。含める場合は、列を追加するマイグレーションと、起動引数（`--width`、`--height`）への反映を同時に行う。含めない場合は、ダイアログに項目を出さない（見せて効かない項目は作らない）。

## 4. 5-2：Forge と NeoForge（5-2a と 5-2b）

### 4.1 導入の方式

spec 0 の 5.3 節のとおり、インストーラを取得して展開し、`install_profile` の processor を自前の実行エンジンで順に実行する。出力のハッシュが宣言されている場合だけ検証する。完了時に、インストーラ、入力、使用した Java の識別情報を完了記録として残す。Forge と NeoForge は同じ実行エンジンを使う。

- processor の実行に使う Java は、インストーラの要件に合うものを選ぶ。ゲームの起動に使う Java と同じとは限らない（調査 2 の 6 節）。該当する Java が未導入のときは、ゲームの Java と同じく Mojang のランタイムを自動で導入して使う（既存の Java の導入処理を使う。私の判断）。
- 実行エンジンで問題が解決できないバージョンがあれば、公式インストーラの `--installClient` を代替案として使うかを、その時点で判断する。初期実装では使わない（spec 0 のとおり）。

### 4.2 対応範囲

- Forge（5-2a）：1.16.5〜1.21.x のうち、実際に導入と起動を確認したビルド。1.12.2 以前は 4.3 節（5-2b）で扱う。
- NeoForge：1.20.1 以降のうち、実際に導入と起動を確認したビルド。
- 確認していないバージョンは、作成ダイアログで選べなくするか、「未確認」と表示する。どちらにするかは builder が決める。
- 1.13.2〜1.16.4 の Forge は、実行エンジンが対応できると確認できた時点で範囲に加える。

### 4.3 旧形式の Forge（1.8.9〜1.12.2）

ユーザーは時々 1.8.9 や 1.12.2 で遊ぶため、このフェーズに含める（2026-10-20 にユーザーが決定。spec 0 の 5.3 節で初期の対応範囲から外していた判断を変更する）。実装は 5-2a の後の 5-2b として行い、5-2a の動作確認が済んでから着手する。

- この形式は universal jar と LaunchWrapper を使い、4.1 節の processor の実行エンジンとは別のアダプターが必要になる（調査 2 の表：「Legacy nested-profile adapter + supplied universal/library payload + LaunchWrapper」）。
- 調査 2 で中身を確認したのは 2847 と 2859 の 2 つのビルドで、それより前のビルドは未確認である。1.8.9 と 1.12.2 の実際のビルドを、実装の最初にインストーラで調べ、形式を確認してから導入の仕組みを決める。
- 旧バージョンのゲームは Java 8 を要求する。ゲームの Java は version JSON の `javaVersion` に従うため、既存の起動処理で選ばれることを確認する（Mojang の旧ランタイムを導入できること）。
- 実機で確認するバージョンは、1.8.9 と 1.12.2 を最優先とする。それ以外の 1.8.9〜1.12.2 は、導入できたものだけを選べるようにする（4.2 節と同じ扱い）。
- NeoForge は 1.20.1 以降のみであり、旧形式の対象ではない。

## 5. 5-3：コンテンツタブ

### 5.1 インスタンスの詳細の構成

インスタンスの詳細（`/instances/:id`）を、タブの構成にする。このフェーズで作るのは「概要」（従来の詳細の内容）と「コンテンツ」の 2 つである。「スクリーンショット」と「ログ」のタブは後のフェーズで加える（タブの並びは、そのとき足せる形にしておく）。

### 5.2 一覧

- 対象は MOD のみ（1.3 節）。
- 1 行に、アイコン（取得できなければ既定の絵）、名前、バージョン、短い説明、有効無効のトグルボタン、更新ボタン、削除ボタンを置く。
- 有効無効は、チェックボックスではなくトグルボタンにする（ユーザーの指示）。無効の MOD は行を薄く表示する。「起動時に読み込まれない」といった説明文は付けない。
- 更新ボタンは小さく簡潔にし、ホバーしたときに「v0.2.1 に更新」のように行き先のバージョンを示す。更新があるときだけ表示する。
- 一覧の上部に、絞り込みの入力、「Modrinth から追加」ボタン、更新があるときだけ「すべて更新（件数）」ボタンを置く。
- 行の表示情報の取得元（私の判断）：Modrinth で特定できた MOD は、Modrinth のプロジェクトの情報（名前、アイコン、説明）と、バージョン番号を使う。特定できない MOD（`local`、オフラインで落とした jar を含む）は、jar の中のメタデータ（`fabric.mod.json`、`quilt.mod.json`、`META-INF/mods.toml`、`META-INF/neoforge.mods.toml`）から名前、バージョン、説明、アイコンを読む。読めないときはファイル名を表示する。読んだ結果は `instance_contents` に列を足して保存し（名前、バージョン番号、説明、アイコンの参照）、ファイルのサイズと更新時刻が変わるまで読み直さない。列の追加はマイグレーションで行う。
- 依存の印と警告の元になる依存関係は、Modrinth のバージョン情報の `dependencies` から得て保存する（`installed_as = dependency` の記録と合わせる）。jar の中の依存の宣言は読まない。このため、`local` の MOD が関わる依存の警告は出ない。
- 一覧はページ分けしない。画面に見えている行だけを描画する方式（仮想スクロール）にする（ユーザーと合意した方針）。数百件でも軽く動くこと。
- 絞り込みは、名前に対する部分一致とする。
- 依存として自動導入された MOD には、小さな印を付ける。他の MOD が依存している MOD を削除または無効にしようとしたときは、警告を出して確認する。

### 5.3 有効と無効

- ディスク上では、ファイル名の末尾に `.disabled` を付けるかどうかで表す（spec 0 の `instance_contents.enabled`）。
- 切り替えは、ファイル名の変更だけで行い、ダウンロードや再計算を伴わない。切り替えの途中で失敗したときに、名前が中途半端な状態で残らないこと。

### 5.4 ドラッグ＆ドロップによる追加

- `.jar` ファイルを、タブのどこにでも落とせる。ファイルを持ってタブに入った時点で、受け皿を表示する。常設の点線枠は置かない。
- 落とされたファイルは `mods/` にコピーし、SHA-1 と SHA-512 を計算して `instance_contents` に記録する。
- 落とされたファイルに対して Modrinth を照会し（`POST /version_files`）、特定できた場合は `provider`、`project_id`、`version_id` を埋める。特定できない場合は `provider = local` とする。オフラインのときは照会せず `local` として記録し、後の更新確認で特定する。
- `.jar` 以外のファイルは受け付けず、理由を示す。同じ名前のファイルがすでにあるときは、上書きせずに確認する。
- 落とされた jar が、そのインスタンスのローダーや Minecraft のバージョンに合うかの検査は、このフェーズでは行わない（jar の中身から確実に判定する方法が一定でないため）。Modrinth で特定できた場合に限り、対応するローダーとバージョンでないときに警告を出す。

### 5.5 ディスクとの照合

- spec 0 の 4.1 節のとおり、ディスクのファイルを正とする。コンテンツタブを開いたときに `mods/` をスキャンし、`instance_contents` との食い違いをハッシュで照合して DB を合わせる。
- ランチャーの外で追加または削除された jar も、次にタブを開いたときに一覧に反映される。
- 大きなフォルダでも画面が固まらないよう、ハッシュの計算は UI のスレッドの外で行い、すでにハッシュを持つ（サイズと更新時刻が変わっていない）ファイルは再計算しない。

## 6. 5-4：Modrinth との連携

### 6.1 画面

ユーザーの要望に合わせて、2 つの入口を持つ。

| 画面 | 内容 |
|---|---|
| コンテンツ（全体） | サイドバーから開く。インスタンスに関係なく MOD を探せる。フィルターは Minecraft のバージョン、ローダー、カテゴリなどを自由に選べる |
| インスタンス別のコンテンツ | インスタンスの「コンテンツ」タブの「Modrinth から追加」から開く。Minecraft のバージョンとローダーを、そのインスタンスの値に固定する（切り替えられない） |

- 全体の画面も、検索の対象は MOD のみとし、`project_type` は `mod` に固定する（1.3 節）。フィルターのカテゴリは MOD のカテゴリである。
- 検索結果の 1 件ごとに、名前、説明、ダウンロード数、カテゴリを表示し、「Modrinth のページをブラウザで開く」ボタンを付ける。ブラウザで開くのは `modrinth.com` のプロジェクトのページに限る。
- 全体の画面では、各 MOD に「インスタンスに追加」と「最後に追加したインスタンスに追加」の 2 つのボタンを置く。前者はインスタンスを選ぶ小さなメニューを出す。選択肢は、その MOD のバージョンとローダーに合うインスタンスだけにする。後者は、最後に追加したインスタンスが合わないときは無効にする。「最後に追加したインスタンス」は `app_settings` に保存する。
- 検索結果は、API がページ単位で返すため、ページ分けまたは「もっと見る」にする。どちらにするかは builder が決める。
- 検索の入力は、入力が止まってから送る（連続した入力ごとには送らない）。

### 6.2 依存 MOD の導入

- MOD を導入するときは、そのバージョンの `dependencies` を調べ、必須（`required`）の依存を再帰的に解決して、まとめて導入する。依存の解決は、そのインスタンスの Minecraft のバージョンとローダーに合う版を選ぶ。
- 確認のダイアログは出さず、黙って導入する（ユーザーの指示）。導入が終わったあとに、「依存 MOD を N 件追加しました」というトースト通知を出す。
- 依存として導入した MOD は、`installed_as = dependency` として記録する。
- 任意（`optional`）の依存は自動では導入しない。
- 非互換（`incompatible`）と宣言された MOD がすでに入っている場合は、導入の前に警告を出して確認する。
- すでに入っている MOD が依存の条件を満たしているときは、再度導入しない。無効（`.disabled`）の MOD は、読み込まれないため、条件を満たしているとは数えない。その MOD が条件に合う版であれば、ダウンロードの代わりに有効にする（私の判断）。
- 循環した依存、ファイルを持たないバージョン、条件に合う版が見つからない依存は、導入を止めて、どの MOD が原因かを示すエラーにする。何も導入されていない状態に戻すこと。

### 6.3 更新の確認

- インスタンスの「コンテンツ」タブを開いたときに、自動で更新を確認する。
- 確認は、インスタンスに入っている MOD のハッシュをまとめて送る 1 回の呼び出し（`POST /version_files/update`）で行う。MOD の数が増えても、リクエストの数は増えない。
- 同じインスタンスの結果は **15 分間キャッシュ** し、その間にタブを開き直しても再確認しない。キャッシュはメモリ上でよい。
- 「更新を確認」ボタンを置き、押したときはキャッシュを無視して調べ直す。
- Modrinth のレートリミットは 1 分あたり 300 リクエストである（調査 4）。`429` が返ったときは、`X-Ratelimit-Reset` の秒数だけ待って自動で再試行する。待っている間は、エラーを出さず、控えめな表示（「あとで確認します」程度）にとどめる。
- 調査 4 で未検証の項目（一度に送れるハッシュの数の上限、レートリミットを超えたときの実際の挙動）は、実装の中で確かめ、結果を記録する。
- オフラインのときは確認せず、最後の結果もないので、更新の表示は出さない。

### 6.4 更新の適用

- MOD ごとの更新ボタンと、「すべて更新」で実行する。
- 無効の MOD も更新の対象にし、更新後も無効のままにする。Modrinth で特定できていない（`local`）MOD は、ハッシュで特定できた場合だけ対象になる。
- `pinned`（バージョンを固定している）MOD は更新の対象にしない。固定の切り替えを画面に出すかは builder が決める。このフェーズで画面に出さない場合でも、列と判定は使う。
- 更新した MOD の依存が増える場合は、6.2 節と同じ規則で依存も導入する。

### 6.5 更新前のバックアップと失敗時の扱い

- spec 0 の `backups`（reason は `pre-update`）と `operations`（準備と確定の 2 段階）を使う。
- 更新の前に、置き換える jar を退避する。新しいファイルのダウンロードと検証（SHA-1 または SHA-512）が済んでから置き換える。途中で失敗した場合は、退避した jar を元の場所に戻し、更新前の状態にする。
- 退避した jar は、更新に成功したあとも一定期間残す。残す期間や数は builder が決める（ユーザーが「元に戻す」操作を行える場合に備える）。「元に戻す」ボタンを画面に出すかは、このフェーズでは決めない。
- `operations` は MOD 1 件ごとに 1 行とする。「すべて更新」は 1 つのタスクとして進捗を出し、中身は MOD ごとの独立した操作の並びとする（私の判断）。
- 「すべて更新」で一部の MOD だけが失敗したときは、成功した MOD はそのままにして、失敗した MOD の名前と理由を、完了後にまとめて示す。

## 7. エラーとオフライン

- Modrinth に接続できないときは、検索と導入と更新の確認は使えない旨を示す。導入済みの MOD の一覧、有効と無効の切り替え、jar の追加と削除は、オフラインでも使える。
- 失敗の表示は、既存の `FailureNotice` の形に合わせる。
- ローダーのメタデータは、`cache/meta/` に ETag つきで保存し、オフラインでは保存済みのものだけで作成と起動を進める（spec 0 の方針）。ローダーのバージョンの一覧が取得できず、保存済みのものもないときは、そのローダーを選べない状態にして理由を示す。

## 8. テスト

- ローダー：公式メタデータの JSON を固定のサンプルにして、プロファイルの解決と起動引数の組み立てを自動テストする。実際のダウンロードを伴う導入は、実機で確認する。
- コンテンツ：有効と無効の切り替え、ドロップ、スキャンとの照合は、一時ディレクトリを使って自動テストする。
- Modrinth：HTTP をモックして、検索、依存の解決（循環、非互換、満たしている依存を含む）、更新の確認と 15 分のキャッシュ、`429` の再試行、更新の失敗時の巻き戻しを自動テストする。
- 画面：作成ダイアログのローダー選択、コンテンツ一覧、更新ボタンのツールチップをテストする。スクリーンショットで見た目を確認し、PR に添付する（過去のフェーズでの教訓）。
- 実機で確認すること：Fabric と Forge それぞれでの導入と起動、MOD を入れた状態での起動、実際の Modrinth での導入と更新。

## 9. この設計で私が決めたこと

次は、ユーザーとの対話で明示的に決まっていない、私の判断である。

1. リソースパックとシェーダーはこのフェーズに含めない。
2. インスタンスの詳細のタブは、このフェーズでは「概要」と「コンテンツ」の 2 つ。
3. 起動中のインスタンスの MOD は変更できない。
4. 任意の依存は自動では導入せず、非互換の MOD がある場合は確認を出す。
5. 検索結果の「最後に追加したインスタンス」は `app_settings` に保存する。
6. 落とした jar を Modrinth で特定できないときは `local` として一覧に残す。
7. Forge と NeoForge のタブは、5-2a が終わるまで「準備中」で選べない（旧形式の Forge は 5-2b まで）。
8. 行の表示情報は、Modrinth で特定できたものは Modrinth から、できないものは jar のメタデータから得る。依存の警告は、Modrinth の依存情報の範囲だけで出す（5.2 節）。
9. 無効の MOD は依存を満たすとは数えず、更新は無効のまま行う（6.2、6.4 節）。
10. processor 用の Java は自動で導入する（4.1 節）。
11. 作成済みのインスタンスのローダーの変更は、このフェーズでは行わない（1.3 節）。
12. `operations` は MOD 1 件ごとに 1 行とする（6.5 節）。
