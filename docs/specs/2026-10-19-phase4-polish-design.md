# フェーズ 4 の仕上げ：タイトルバー、ゲームの停止、通知、設定の見た目の設計

- 作成日：2026-10-19
- 状態：承認済み（2026-10-19）
- 前提：`docs/specs/2026-10-19-phase4-instance-ui-design.md`（PR #7）。この仕上げは、その上に積む（ブランチ `feat/phase4-polish`）
- 参考：Modrinth App のタイトルバー（利用者が示したスクリーンショット）

## 1. 目的と範囲

PR #7 の実装を実機で触った利用者から、「UI が直感的でない、作り込みが足りない」という指摘があった。この文書は、その指摘のうち、次の 5 つをまとめて直す。

1. ウィンドウのタイトルバーを、アプリの画面と一体の独自のものにする（Modrinth App の形）。
2. ゲームを、ランチャーから停止できるようにする。
3. 操作の失敗や警告を、画面のレイアウトをずらさないトーストで出す。
4. ドロップダウンのスクロールバーの見た目を直す。メモリの設定に、スライダーを足す。
5. インスタンスのフォルダ（ゲーム、`mods`、`screenshots`、ワールド）を、ワンクリックで開けるようにする。

### 1.1 想定する使い方

ユーザー（開発者本人）は、複数のインスタンスを同時に起動することがある。どの画面にいても、動いているゲームが分かり、そこから止められることが大事である。

### 1.2 目標でないこと（範囲外）

| 項目 | 扱い |
|---|---|
| スキンの専用タブとプレビュー、スキンの PNG のドラッグ＆ドロップ | 次の設計（仕上げ 2） |
| スクリーンショットのタブ、スクショの取り込みのドラッグ＆ドロップ | その次の設計（仕上げ 3） |
| MOD の一覧と、jar のドラッグ＆ドロップによる導入 | フェーズ 5 の「コンテンツ」タブの設計に必ず入れる（ローダーが必要なため） |
| macOS と Linux での独自のウィンドウボタン | 範囲外。この 2 つの OS では、OS 標準のタイトルバーを使い続ける（私の判断） |
| メモリの自動設定 | フェーズ 9 |

### 1.3 してはいけないこと

- ゲームの停止で、別のプロセスを止めない。プロセスの ID が再利用されていても、このインスタンスのゲームとは別のプロセスには、何も送らない。
- 確認なしに、ゲームを強制終了しない（セーブが失われるおそれがあるため）。
- 動きのせいで、操作の邪魔をしない。「動きを減らす」設定のときは、移動をやめて不透明度の変化だけにする。

## 2. タイトルバー

Windows では、OS 標準のタイトルバーをやめ（`decorations: false`）、アプリの上端に `AppBar` を置く。macOS と Linux では、標準のタイトルバーのままにし、`AppBar` はその下に置く（中身は同じで、ウィンドウボタンだけが無い）。

### 2.1 構成（左から）

| 部分 | 内容 |
|---|---|
| ロゴと名前 | 「Nexora」 |
| 戻る・進む | ルーターの履歴を戻る・進む。行き先が無いときは無効にする |
| 今の画面の名前 | ホーム、インスタンス、アカウントなど。詳細の画面ではインスタンスの名前 |
| 空き | ウィンドウの移動に使うドラッグ領域（`data-tauri-drag-region`）。ダブルクリックで最大化と元に戻す |
| タスクの丸いボタン | 今は右下の `TaskTray` にある、ダウンロードとインストールの進み具合。進行中のタスクがあるときだけ進捗の輪を出し、押すとポップアップで一覧を出す。`TaskTray` の中身を再利用し、右下の表示はなくす |
| 実行中の表示 | 2.2 節 |
| ウィンドウボタン | 最小化、最大化と元に戻す、閉じる（Windows のみ） |

### 2.2 実行中の表示

- 動いているゲームの数だけ、緑の点を並べる。1 つのときは、インスタンスの名前と赤い停止ボタン、ログを開くボタンを持つ「ピル」の形で出す。2 つ以上のときは、点が並んだ 1 つのピルにまとめる（3 つ目以降の見せ方は私の判断：点は 3 つまで出し、それ以上は「+N」）。
- ピルを押すと、小さなポップアップが開く。動いているインスタンスが 1 行ずつ並び、各行に、名前、停止ボタン（赤）、ログを開くボタンを置く。行を押すと、そのインスタンスの詳細に移る。
- 動いているゲームが 0 件になったら、ピルは動きながら消える。停止を頼んで終了を待っているインスタンスは、終了するまで一覧に残し、その行とピルに「終了を待っています」の表示を出す（私の判断）。
- 動いているゲームの一覧は、既存の `useRunning`（`list_running` とイベント）を使う。

### 2.3 ウィンドウの設定

- Windows の `tauri.windows.conf.json` に `decorations: false` を足す。Mica の素材と透明は、そのまま使う。
- ウィンドウボタンは、`@tauri-apps/api/window` の最小化、最大化の切り替え、閉じるを呼ぶ。そのための権限を `capabilities/main.json` に足す。
- 独自のボタンにすると、Windows 11 の「最大化ボタンにマウスを乗せると出る配置候補（スナップレイアウト）」が使えなくなるおそれがある。builder は、実装の最初に実機で確かめ、結果を報告する。使えなくなる場合の対策（独自のボタンを諦める、など）は、利用者に聞く。
- ウィンドウの端をつかんで大きさを変えられることも、実機で確かめる。
- この確認を、タイトルバーの作業の最初に行う（使い捨ての試作でよい）。結果の扱いは、次のとおりにする（私の判断）。スナップレイアウトが使えなくなるだけなら、独自のボタンのまま進め、結果を報告する。端での大きさの変更や、ウィンドウの移動が壊れる場合は、macOS と Linux と同じ形（OS 標準のタイトルバーのままで、`AppBar` はその下に置く）に切り替え、その理由を報告する。

### 2.4 動き

- ピルとポップアップ、点の出入りと並び替えには、Motion（`motion/react`）を使う。利用者が認めている（「複雑なところはどんどん Motion を使う」）。それ以外の簡単な動き（ホバーの色の変化、メニューの出入り）は、これまでどおり CSS と React Aria で作る。
- アプリの全体を `MotionConfig reducedMotion="user"` で包み、「動きを減らす」設定に従う。
- 入れたあとに、バンドルのサイズを実測して報告する。増えた量が大きすぎれば、`LazyMotion` に切り替える。

## 3. ゲームの停止

利用者が決めた方針：まずゲームに「閉じて」と頼み、閉じなければ確認してから強制終了する。

### 3.1 core

`Launcher::stop_instance(instance_id: &str, force: bool) -> Result<(), CoreError>` を足す。

- 対象は、`running_sessions` に記録された pid とプロセスの開始時刻だけである。ランチャーを再起動した後に引き継いだ（`reattach` した）ゲームにも、同じ方法で届くため、子プロセスのハンドルは持たない。ゲームは Java を直接起動しているため、記録された pid がウィンドウを持つプロセスである。Windows では、その pid が持つ、表示中で所有者の無いトップレベルのウィンドウに、`WM_SYSCOMMAND`（`SC_CLOSE`）を送る（`EnumWindows` で探す）。非表示の補助ウィンドウは飛ばす。該当するウィンドウが見つからなければ、何も送らずに戻り、UI は 10 秒後の確認に進む。実行前に、今の同じ pid のプロセスの開始時刻が記録と一致することを確かめる（既存の `process_start_ms`）。一致しなければ、何も送らずに「すでに終了している」として扱う。
- `force = false`：Windows では、そのプロセスの表示中のトップレベルのウィンドウに `WM_SYSCOMMAND`（`SC_CLOSE`）を送る（`windows-sys` を使う）。macOS と Linux では、SIGTERM を送る。どちらも、ゲームが閉じるのを待たずに戻る。
- `force = true`：プロセスを強制終了する（`sysinfo` の `Process::kill`）。
- ゲームが終了した後の記録（最後に遊んだ時刻、プレイ時間）は、既存の終了の検知に任せる。この関数では何も書かない。
- macOS と Linux で「閉じて」と頼む方法が効かない場合（SIGTERM で Minecraft がセーブして終了するとは限らない）、builder は実機で確かめ、効かなければ強制終了だけにして、その理由を spec に書く。

### 3.2 UI

- 停止ボタンは、ピル、ポップアップの行、およびインスタンスの一覧と詳細の `PlayButton`（プレイ中の表示にマウスを乗せると赤い「停止」に変わる）に置く。
- 押すと `stop_instance(force=false)` を呼び、ボタンを「終了を待っています」の表示にする。10 秒たってもゲームが終了しなければ、確認のダイアログを出す：「ゲームが閉じません。強制終了すると、最後のセーブ以降の進みが失われるおそれがあります。」標準の操作は「待つ」、もう 1 つが「強制終了」。強制終了を選ぶと `force=true` で呼ぶ。
- ゲームが終了したら（既存のゲームの終了のイベント）、待ちの表示を消す。
- 「終了を待っています」の状態は、インスタンスごとに 1 つの共有の状態として持ち（`useRunning` の近くに置く）、ピル、ポップアップの行、`PlayButton` のすべてが同じ状態を見る。確認のダイアログは、1 回の停止の依頼につき 1 度だけ出す。利用者が「待つ」を選ぶか、何も選ばずに閉じたときは、待ちの状態を続け、その行とピルの停止ボタンを「強制終了」に変える。そこからは、利用者が押したときだけ強制終了する。ランチャーを閉じたときの動きは変えない（ゲームはそのまま動き続け、次の起動で引き継ぐ）。（以上は私の判断）

## 4. トースト

- 画面の右下に、`ToastRegion` を 1 つ置く。React Aria Components の `Toast` が使えるなら、それを使う（`react-aria-components` は 1.22）。使えなければ自作してよい。出入りの動きは Motion を使う。
- 次は、トーストで出す。画面のレイアウトを動かさない。
  - インスタンスの一覧の操作（複製、削除、起動）の失敗と、削除の「フォルダが一部だけ削除された可能性」の案内。
  - アカウントの操作（削除など）の失敗。
  - インスタンスの設定の保存の成功（「保存しました」）と失敗。
  - ゲームの停止の失敗。
- 次は、これまでどおり、その場に出す。
  - ダイアログの中の失敗（スキンの変更、ログイン、複製の確認など）。
  - フォームの入力の誤り（名前が空、メモリの範囲外など）。
  - 状態そのもの（ログインし直しが必要、インスタンスが壊れている、など）。
- 文言は、これまでの `errorText`（エラーコードを日本語と英語の文にする仕組み）を使う。
- 表示の長さ：成功と情報は 5 秒、失敗は 8 秒で消える（私の判断）。マウスを乗せている間とフォーカスがある間は、消えない。閉じるボタンを付ける。
- 同時に出すのは最大 3 つまで（私の判断）。それ以上は、古いものから消す。
- 読み上げ：失敗は `role="alert"`、それ以外は `role="status"`。

## 5. 見た目の修正

### 5.1 スクロールバー

`Select` の一覧（`max-h-72 overflow-auto`）のスクロールバーが、OS 標準のままで、アプリの見た目と合っていない（私の推測。利用者の指摘は「ドロップダウンメニューのスクロールバー」）。アプリ全体の細いスクロールバー（色はトークン、`scrollbar-width: thin` と `scrollbar-color`）をひとつ定義し、`Select`、ポップアップ、トーストの一覧など、スクロールする所に適用する。builder は、実機のスクリーンショットで、直ったことを確かめる。

### 5.2 メモリのスライダー

- インスタンスの詳細のメモリ（手動）に、スライダーを足す。数値の入力と同期する（どちらを動かしても、もう一方が追従する）。
- スライダーの範囲は 512 MB から、マシンの物理メモリ（上限は 65536 MB）まで。刻みは 256 MB（私の判断）。数値の入力は、これまでどおり 512〜65536 MB を受け付け、スライダーの範囲を超えた値のときは、スライダーを右端に置く。
- 物理メモリは、core の `sysinfo` で読み、command `system_memory_mb() -> u32` で返す（`sysinfo` は既に使っている）。
- React Aria の `Slider` を使う。キーボードで動かせること、現在の値を読み上げることを確かめる。

## 6. フォルダを開く

- core に command `open_instance_folder(instance_id, kind)` を足す。`kind` は `game`、`mods`、`screenshots`、`saves` のどれか。
- フォルダのパスは、core がインスタンスの `dir_name` から組み立てる（UI から任意のパスを受け取らない）。フォルダが無いときは作ってから開く（私の判断：`mods` は、ローダーを入れるまで無いが、空のフォルダを作っても害は無い）。
- 開くのは、`tauri-plugin-opener` の Rust 側（`OpenerExt::open_path`）で行い、UI に「任意のパスを開く権限」は与えない。
- 置き場所：インスタンスの詳細の見出しの横に、4 つのボタン（ゲーム、mods、スクショ、ワールド）。一覧の行のメニューには、「フォルダを開く」を足す（ゲームのフォルダだけ）。

## 7. テストと確認

- core：停止（開始時刻が違う pid には何も送らない、強制終了、すでに終了している場合）、フォルダを開く（種類の検証、無いときに作る）、物理メモリの command。
- UI：トースト（出る、消える、ホバーで消えない、3 つを超えない）、タイトルバー（戻る・進むの無効、実行中のピルが 0 件 / 1 件 / 2 件で変わる、ポップアップの停止）、停止の流れ（10 秒後の確認）、スライダーと数値の同期、フォルダを開くボタン。
- 手動の確認（実機）：独自のタイトルバーで、移動、最大化、端での大きさの変更、スナップレイアウトの有無。停止（ワールドが保存されて終了すること）と、強制終了の確認。スクロールバーとトーストの見た目。スクリーンショットで、利用者が確認できる形にして渡す。

## 8. builder に任せること

- `AppBar`、`RunningPill`、`ToastRegion` などのコンポーネントの分け方と、モジュールの構成。
- ピルとポップアップ、トーストの見た目の詳細（Modrinth App を参考にし、デザインのトークンだけを使う）。
- トーストの実装に React Aria の `Toast` を使うか、自作にするか。
- 戻る・進むの無効の判定の方法（ハッシュルーターの履歴の位置から求める、など）。
- macOS と Linux で「閉じて」と頼む方法（3.1 節の確認の結果による）。

## 9. 実装での判断

builder が、実装の中で決めたこと。

- トーストは、React Aria の `Toast` を使わず自作した。RAC 1.22.1 の `Toast` は、役割（role）とキューの扱いが、この設計の書き方と違うため。
- タイトルバーのダブルクリックは、自前で処理する。Tauri のドラッグ用スクリプトとの二重の切り替え（最大化してすぐ元に戻る）を避けるため。
- 「ログ」ボタンが開くのは、Minecraft の `latest.log` ではなく、ランチャーが取り込んだログのフォルダ（`logs/game/<id>`）。
- Windows かどうかは、`app_info` の os で判定し、取れないときはブラウザのプラットフォームの値にフォールバックする。
- 実機のウィンドウでの確認（タイトルバー、スナップレイアウト、Mica など）は、agent では行っていない。利用者が手動で確認する。
- motion のバンドルは gzip で約 42 kB 増えた。コード分割は、今回は行わず、後の課題とする。
- 強制終了に失敗したときは、停止中の表示から、待機（idle）の状態に戻す。
- Windows の閉じる依頼は、`WM_CLOSE` ではなく `WM_SYSCOMMAND`（`SC_CLOSE`）にした。タイトルバーの X ボタンや Alt+F4 が送るのがこれである。LWJGL 2.9.x（Minecraft 1.8.9、1.12.2）は `SC_CLOSE` だけを閉じる要求として扱い、`WM_CLOSE` ではウィンドウが壊れるだけで JVM が動き続ける。実機で、1.8.9、1.12.2、26.3 が `SC_CLOSE` で正常に終了する（`Stopping!`、終了コード 0）ことを確かめた。NVIDIA や IME の非表示の補助ウィンドウを壊さないよう、表示中で所有者の無いウィンドウだけに送る。
