# スキン画面とヘッダーまわりの整理 設計

アカウント画面の中にあるスキン変更のダイアログを、サイドバーに独立した「スキン」画面へ作り替える。あわせて、タイトルバーとサイドバーの見た目の食い違いを整える。UI の方針は、既存の spec（フェーズ 4 の UI 設計、仕上げ）に従う。食い違う場合は、この文書を優先する。

## 1. 目的

- スキンを「見て選ぶ」画面にする。Modrinth App のスキン画面のように、左に大きな 3D のプレビュー、右に「保存したスキン」と「デフォルトのスキン」のカードを並べ、押せば適用される。利用者は、見てすぐ分かることを最も重視している。
- 今は、アカウント画面から開くダイアログで「ファイルを選ぶ → classic か slim を選ぶ → 変更」しかできない。保存したスキンの一覧も、プレビューも、マントもない。
- あわせて、タイトルバーの左端とサイドバーの項目の揃い、ページ名の見せ方（押せるパンくず）、共通設定ページの名前が出ないバグ、サイドバーのアイコンの大きさを直す。

## 2. 方針（利用者が決めたこと）

- スキンはサイドバーに**独立した画面**として置く（アカウント画面の中のタブにはしない）。
- 画面の構成は Modrinth App のスキン画面に倣う。左がプレビュー、右が「保存したスキン」と「デフォルトのスキン」。「保存したスキン」の先頭は「スキンを追加」のカードで、PNG のファイルをドラッグして追加できる。選んでいるスキンにはチェックを付ける。
- 「スキンを編集」は**軽いもの**だけ。名前の変更、classic と slim の切り替え、ファイルの差し替え、削除。ドットを塗るエディタは作らない。
- マントを含める（持っているマントの一覧と、着ける／外す）。
- 他のプレイヤー名からスキンを取ってくる機能は要らない。
- デフォルトスキンの画像は、アプリに同梱してはいけないかもしれない。同梱せず、外から取ってくる。
- 未ログインのアカウントの扱いは任された（4.8）。
- 説明の文や副次的なラベルはなるべく置かない。場所と形（札、アイコン、チェック、空の丸と塗りの丸など）で伝える。補足は、結果が予想できない操作に限る。

## 3. 範囲

### 3.1 含めるもの

- 「スキン」画面（`/skins`）と、サイドバーの項目の追加。
- 保存したスキンのライブラリ（このパソコンの中。アカウントをまたいで使える）。
- 3D のプレビュー（ドラッグで回転）。
- デフォルトスキンの表示と適用。
- マントの一覧と切り替え。
- 軽い編集（4.5）。
- 既存の `ChangeSkinDialog` の撤去。アカウント画面の「スキンを変更」は、スキン画面への移動に置き換える。
- ヘッダーまわりの整理（5 章）。

### 3.2 含めないもの

- スキンに直接ドットを塗るエディタ。
- プレイヤー名や URL からスキンを取り込む機能。
- スキンの共有、公開、オンラインの検索。
- オフラインアカウントのスキンの適用（Mojang のサービスに送れないため）。

### 3.3 失敗とみなすこと（動いていても失敗）

- 画面に説明の文が並ぶこと。
- 適用や追加のたびに、一覧やプレビューが跳ねたり点滅したりすること。押した後に、古い状態が一瞬戻ってから新しい状態になること（直近の仕上げで直した型の不具合を、新しい画面で作り直さない）。
- ラベルが途中で折り返すこと、スクロールバーが出て中身が押されること。
- 同梱できないかもしれない画像を、アプリに入れてしまうこと。
- 適用に失敗したのに、成功したように見えること。

## 4. スキン画面

### 4.1 画面の構成

- 左の列にプレビュー。3D のモデルをドラッグで回せる。プレビューの下に、classic と slim の表示、使っているアカウントの切り替え、マントの選択を置く。
- 右の列に、上から「保存したスキン」と「デフォルトのスキン」。それぞれ見出しを付け、カードを格子に並べる。幅に応じて列数が変わる。
- 「保存したスキン」の先頭は「スキンを追加」のカード（点線の枠、プラスのアイコン、「スキンを追加」の一語）。ここへ PNG をドラッグして離すか、押してファイルを選んで追加する。
- カードには、そのスキンを着た人形の絵（正面）を出す。いま着ているスキンは、枠を強調してチェックを付ける。
- カードを押すと、そのスキンが適用される。確認のダイアログは挟まない（元に戻すのも、別のカードを押すだけなので）。適用の最中は、そのカードに進行中の印を出し、ほかのカードも押せないようにする。

### 4.2 現在のスキンの扱い

- 画面を開いたとき、使っているアカウントの現在のスキンを取得してプレビューに出す。
- 現在のスキンの画像が保存ライブラリに無ければ、一度だけライブラリに追加する（利用者が追加しなくても、いま着ているものがカードに出るようにする）。これは仕様としての**私の判断**で、変えたければ指示をもらう。
- 同じ画像かどうかは、PNG の内容の同一性で判断する（ファイル名ではない）。

### 4.3 保存したスキンのライブラリ

- 1 件に、画像（PNG）、名前、モデルの種類（classic か slim）、追加した日時を持つ。
- 保存先はこのパソコン（アプリのデータの場所）。形式（DB の表かファイルか）はビルダーが決める。
- 追加の入口は、「スキンを追加」のカードへのドラッグと、押してのファイル選択の 2 つ。どちらも同じ検証を通す（64×64 または 64×32、64 KiB まで。既存の `MAX_SKIN_BYTES` と同じ上限）。
- 追加するとき、モデルの種類は、画像から判定できるなら自動で決め、判定できなければ classic とする。あとから編集で変えられる。判定の方法はビルダーに任せる。
- 名前は、既定でファイル名（拡張子を除く）。
- 上限の件数は設けない。

### 4.4 適用

- 適用は、既存の `change_skin`（Mojang のサービスへ PNG と variant を送る）を使う。401 での再取得と 429 の扱いも、既存のものをそのまま使う。
- 適用に成功したら、現在のスキンの表示（プレビューとチェック）を取り直す。取り直しが終わるまで進行中のままにし、古い表示が一瞬戻らないようにする。
- 失敗は、トーストで理由を出す（既存の `FailureNotice` と同じ流儀）。

### 4.5 軽い編集

- 保存したスキンのカードから、次ができる。名前の変更、classic と slim の切り替え、ファイルの差し替え、削除。入口は、カード上の小さなメニューのボタン。
- 削除は、保存ライブラリからだけ消す。Mojang 側のいま着ているスキンは変えない。いま着ているスキンを消してもよい。
- 3D のプレビューの上でスキンを編集する機能は作らない。
- 編集で classic と slim を切り替えた場合、**そのスキンがいま着ているものなら**、適用し直す（Mojang 側の variant を変えるため）。ほかのスキンなら、ライブラリの記録だけを変える。

### 4.6 デフォルトスキン

- 画像は同梱しない。取得元は次のいずれかで、**先に実際に確かめてから決める**（ビルダーの最初の作業）。
  - A（私の案、未確認）: ゲーム本体の jar（ランチャーが Mojang から取得するもの）に入っているデフォルトスキンの画像を取り出す。取得元が公式のまま、同梱もしない。置き場所はバージョンで違う可能性があり、確かめる。
  - B: Mojang の公開の URL（textures.minecraft.net）から取る。URL の安定性は未確認。
- 取得できなかったときの見せ方は、名前だけのカードを出して、押すと取得を再試行する形にする。
- 画像は取得後にキャッシュし、毎回ネットワークに出ない。キャッシュしたものを同梱の代わりにアプリに入れない。
- 適用は、保存したスキンと同じ経路（`change_skin`）。デフォルトのスキンを適用しても、ライブラリには追加しない。

### 4.7 マント

- 持っているマントの一覧と、いま着けているものを、Mojang のサービスから取得する。「着ける」と「外す」の切り替えも同じ。
  - 着ける: `PUT /minecraft/profile/capes/active`（ミラーの情報で存在を確認。公式の資料では未確認）。
  - 一覧の取得: プロフィールの取得結果に `capes` の配列が入っているはず（知識による。未確認）。
  - 外す: 公式の資料で確かめる（`DELETE` と考えているが未確認）。
- 持っているマントが 0 のときは、マントの選択の場所を出さない（説明の文も置かない）。
- プレビューの人形に、着けるマントを映す。マントの画像の取得先は、プロフィールの `capes[].url`。
- 切り替えの最中の見せ方は、スキンの適用と同じ（進行中の印、取り直しが終わるまで進行中のまま）。

### 4.8 未ログインのアカウント（私の判断）

- プレビュー、保存したスキンの閲覧と追加、編集は、ログインしていなくてもできる。
- 「適用」と、マントの取得と切り替えは、ログインが必要なアカウントでは無効にする。カードの押下を受けつけず、画面の上にログインへの導線（ボタン 1 つ）を出す。説明の文は置かない。
- オフラインのアカウント（Microsoft アカウントでないもの）は、Mojang のサービスに送れないので、適用を無効にする。ライブラリは使える。
- アカウントが 1 つもないときは、画面全体を空の状態（ログインのボタンだけ）にする。

### 4.9 3D のプレビュー

- 既製のライブラリを使う前提で、選定はビルダーに任せる。条件は次のとおり。
  - Tauri（WebView2）の中で動く。ネットワークの CDN に依存しない（依存関係としてアプリに含める）。
  - ライセンスがアプリの配布に使える。
  - ドラッグで回転でき、classic と slim の両方、マントの表示ができる。
  - 動きを減らす設定（`prefers-reduced-motion`）では、自動で回る動きを止める。
  - 画面を離れたときに、描画を止める。
- 描画に使う画像は、ライブラリの PNG か、現在のスキンの URL から。

### 4.10 サイドバーとアカウント画面

- サイドバーに「スキン」の項目を足す。位置は、「探す」と「アカウント」の間とする（私の判断）。アイコンは、衣服のアイコン（Phosphor の `t-shirt` など）をビルダーが選ぶ。塗りの版も既存の項目と同じ流儀で用意する。
- アカウント画面の「スキンを変更」ボタンは、スキン画面への移動に置き換える。ダイアログと、そのテストは撤去する。
- 画面の名前は、ヘッダーの名前の表示（5.2）にも出る。

## 5. ヘッダーまわりの整理

### 5.1 左端の揃え

- 今は、タイトルバーのロゴが左から 12px、サイドバーのアイコンは 24px（ナビの余白 12px と項目の余白 12px）にある。ロゴの左端をサイドバーのアイコンの左端に、「Nexora」の文字の左端をサイドバーのラベルの左端に揃える。
- 揃える対象は、**横方向の位置（縦の線）**。「縦の位置があっていない」という指摘を、このように読んだ（私の解釈）。実装後にスクリーンショットで確認してもらう。
- 揃えたことで、戻る・進むのボタンとページ名が右へずれる。幅が足りないとき、ページ名が先に省略される。

### 5.2 押せるパンくず

- 戻る・進むのボタンの右にあるページ名を、パンくずにする。最後の要素以外は押せる（リンク）。例：「インスタンス > Forge 26.3」（「インスタンス」を押すと一覧に戻る。「Forge 26.3」は今の画面で、押せない）。
- 例の「Forge 26.3」は、インスタンスの名前と読んだ（私の解釈）。
- 画面ごとの並び（ビルダーが i18n の既存の語を使う）。
  - ホーム、インスタンス（一覧）、共通設定、探す、スキン、アカウント、設定：1 要素（押せない）。
  - インスタンスの詳細：「インスタンス > {インスタンス名}」。
  - インスタンスへの Modrinth の追加画面：「インスタンス > {インスタンス名} > Modrinth」（私の判断。語は既存の画面の見出しに合わせる）。
- 最後の要素が先に省略される。長いインスタンス名でも、「インスタンス」の要素は縮めない。
- 現在の画面の要素には、`aria-current="page"` を付ける。区切りの記号は装飾（スクリーンリーダーには読ませない）。
- インスタンスの名前が届くまでの間は、「インスタンス」だけを出し、届いたときに名前を足す（既存と同じ）。このとき、名前が出る場所の幅で、ほかの要素が動かないこと。

### 5.3 共通設定のページ名

- 今は、共通設定ページ（`/sync`）で、ページ名が空になる。原因は、`AppBar.tsx` の `SECTIONS` と `NavKey` に `sync` が入っていないこと。パンくずに作り替えるときに、`sync`（と新しい `skins`）を含める。
- 同種の漏れを防ぐため、サイドバーの項目の一覧とパンくずの対応が一致することを、テストで確かめる。

### 5.4 サイドバーのアイコン

- 「タブのアイコン」を、サイドバーの項目のアイコン（今は `size-4`）と読んだ（私の解釈）。もう少し大きくする。まず `size-5` とし、項目の高さ（`h-10`）と文字の大きさとの釣り合いをスクリーンショットで見て、ビルダーが決める。
- 選択中の塗りのアイコンも同じ大きさにする。大きさが変わっても、項目の幅や高さ、文字の位置が変わらないこと。
- インスタンスの詳細のタブのアイコンが対象だった場合は、指摘をもらって別に直す。

## 6. ビルダーの確認で決めたこと（私の判断）

ビルダー役が計画の前に挙げた疑問への答えである。

- **現在のスキンの取得**：プロフィールの取得は既にある（`auth::minecraft::profile`。スキンの URL と variant を読み、`get_skin` と `get_skin_variant` の命令が使っている）。足すのは `capes`（id、URL、状態）の読み取りだけで、新しい取得経路は要らない。トークンの更新と再試行は既存のものを使う。
- **classic と slim の優先**：現在のスキンは、プロフィールの variant を**正**とし、画像からの判定は使わない。ファイルを追加したときだけ、画像から判定し、判定できなければ classic とする。
- **取り込みと削除の衝突**：4.2 の取り込みは、「アカウントごと、画像の内容ごとに一度だけ」とする。取り込んだ（または利用者が削除した）画像の記録を残し、削除したスキンが、画面を開くたびに戻らないようにする。記録の形はビルダーが決める。
- **ファイルの差し替え**：同じカード（同じ id）のまま、画像と内容の識別だけを新しくする。いま着ているスキンなら、variant の切り替えと同じように適用し直す。
- **アカウントの切り替え**：チェックは、選んでいるアカウントの現在のスキンで決める。ライブラリは共通。適用や切り替えの最中は、アカウントの切り替えを無効にする（途中で別のアカウントへ移ると、進行中の印の持ち主が曖昧になるため）。
- **「未ログイン」の判定**：既存の `needsLogin`（保存された状態）と、アカウントの種類（Microsoft かどうか）で、画面を開いた時点から無効にできる。401 を受けてからの判定には頼らない。適用中に 401 が来たら、既存のとおり一度更新して再試行し、それでも駄目なら失敗のトーストを出す。
- **デフォルトスキンの数と、取得元が使えなかったとき**：取得元が出すものを**すべて**並べる。A も B も使えなかったときは、「デフォルトのスキン」の見出しの下に再試行のカード 1 枚だけを出す（名前だけのカードを並べない）。取得元の確認は、ビルダーの最初の作業で、結果が出るまで、デフォルトスキンの作業には進まない。
- **3D のマントの表示**：必須ではない。候補のライブラリがマントを 3D で描けないときは、プレビューのマントを諦め、マントの選択のカードに平らな画像を出す。ライブラリの選定は、スキンの 3D と classic／slim を最優先にする。

## 7. 決まっていないこと（ビルダーに任せる）

- ライブラリの保存形式（DB かファイルか）、画像の同一性の判断（ハッシュの種類）。
- 3D の描画ライブラリの選定。
- デフォルトスキンの取得元（4.6 の A か B）。確かめた結果で決める。
- マントの API の細部（`DELETE` の有無、一覧の形）。公式の資料で確かめて、違えばこの文書を直す。
- classic と slim の自動判定の方法。
- サイドバーのアイコンの選定と、アイコンの大きさの最終値。

## 8. 検証

- 自動のテスト：ライブラリの追加、編集、削除。適用が成功と失敗のとき、取り直しが終わるまで進行中のままであること。未ログインでの無効化。パンくずの並びと、サイドバーとの対応。
- 目で見る確認（実際のウィンドウ、日本語と英語、ライトとダーク）：
  1. タイトルバーの左端とサイドバーの左端が揃っている。
  2. 長いインスタンス名でも、パンくずが 1 行に収まる。
  3. スキンを押して適用したとき、一覧とプレビューが点滅しない。
  4. ドラッグでスキンを追加できる。
  5. ウィンドウの幅を変えても、ラベルが折り返さない。
- 実機の確認が要るもの：実際の Mojang アカウントでの適用とマントの切り替え（自動のテストでは確かめられない）。
