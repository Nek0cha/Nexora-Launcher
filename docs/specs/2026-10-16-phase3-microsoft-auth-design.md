# フェーズ 3：Microsoft 認証とアカウント管理の設計

- 作成日：2026-10-16
- 状態：承認済み（2026-10-16）
- 前提：`docs/specs/2026-10-15-nexora-architecture-design.md`（spec 0）、`docs/specs/2026-10-15-phase2-vanilla-launch-design.md`（spec 2）
- 根拠：`docs/research/03-microsoft-auth.md`（調査 3）

## 1. 目的と範囲

フェーズ 3 の終了時点で、次のことができる状態にする。

1. アカウント画面から、Microsoft アカウントでログインしてアカウントを追加できる。ログインはシステムブラウザで行う。
2. 複数のアカウントを追加し、使うアカウントを切り替え、削除できる。
3. プレイボタンを押すと、使用中のアカウントの本物のセッションで Minecraft が起動する。トークンの期限が切れていれば、起動の前に自動で取得し直す。
4. ログインし直す必要があるときは、プレイボタンを押した時点で画面の中央にダイアログを出す。ダイアログからログインすると、そのまま起動する。
5. 一度正常に認証できたアカウントは、ネットワークに接続できないときに「オフラインで遊ぶ」で起動できる。
6. アカウントの一覧とサイドバーに、各アカウントの現在のスキンの顔を表示する。
7. 起動に使う argfile に、アクセストークンが書き込まれない（フェーズ 2 で後回しにした M-3）。

### 1.1 想定する使い方

ユーザー（開発者本人）は、普段はメインのアカウント 1 つで遊び、まれにサブのアカウントに切り替える。このため、次の方針とする。

- アカウントの切り替えは、目立つ場所に置かない。サイドバーには使用中のアカウントを小さく表示し、切り替えはアカウント画面で行う。
- アカウントの数に上限は設けない。ただし、UI と動作の確認は 2〜3 件を想定すれば足りる。

### 1.2 前提となる外部の状況

- Azure へのアプリの登録と、Minecraft API の利用申請（aka.ms/mce-reviewappid）は、2026-10-16 に完了している。審査の結果はまだ出ていない。
- 審査に通るまでは、Microsoft と Xbox のログインは成功しても、Minecraft Services の `login_with_xbox` が HTTP 403「Invalid app registration」を返すと想定する（調査 3 の 4 節）。このため、フェーズ 3 の実装は、最後の段だけを本物のサービスで確認できない状態で進める。
- 審査に通るまでの開発には、フェーズ 2 の開発用のオフラインアカウントを引き続き使う。

### 1.3 範囲外

| 項目 | 扱うフェーズ |
|---|---|
| スキンの変更 | 4 |
| フェーズ 2 で後回しにした M-3 以外の項目（`.part` の掃除、`COM0` と `LPT0`、ゲームの出力の 1 行の長さの上限、`fetch_all` の失敗時の扱い、Java のファイルの検証、ホームの選択） | それぞれ関係するフェーズ |
| デモ版（体験版）での起動 | 対象外。所有していないアカウントには公式の体験版のページを案内するだけにする |
| 資格情報ストアに収まらない refresh token を複数の件に分けて保存する方式 | 必要と分かった時点で別途設計する（spec 0 の 6.3 節） |

## 2. 構成

### 2.1 モジュール

`nexora-core` に `auth/` を追加する（spec 0 の 3.2 節の `auth/`）。

| モジュール | 役割 |
|---|---|
| `auth/oauth.rs` | PKCE、認可 URL の組み立て、ループバックでの待ち受け、コードの交換、refresh、デバイスコードフロー |
| `auth/xbox.rs` | Xbox Live ユーザートークン、XSTS、XErr の分類 |
| `auth/minecraft.rs` | `login_with_xbox`、所有権の確認、プロフィールの取得、スキンの画像の取得 |
| `auth/store.rs` | OS の資格情報ストアへの refresh token の読み書き。テストではメモリ上の実装に差し替える |
| `auth/accounts.rs` | `accounts` テーブルの読み書き、使用中のアカウントの切り替え、削除 |
| `auth/session.rs` | アカウントごとのトークンのキャッシュと更新のロック。起動用の `LaunchSession` を作る |

`Launcher` の `current_session` は `auth/session.rs` を呼ぶように置き換える。

### 2.2 OAuth の実装方法

`oauth2` クレートは使わず、PKCE とトークンの交換を自前で実装する。理由は次のとおり。

- `oauth2` 5.0 は reqwest 0.12 に依存し、本体の reqwest 0.13 と合わない（spec 0 の 6.4 節）。
- 必要な処理は、乱数の生成、SHA-256、base64url、フォームの POST だけで、量が少ない。

追加する依存は、`sha2`、`base64`、`rand`（または `getrandom`）を想定する。最終的な選定は実装計画で行う。

HTTP は、フェーズ 2 の `Http`（reqwest 0.13）を使う。トークンのエンドポイントへの要求では、リダイレクトを追わない。

### 2.3 エンドポイントの差し替え

フェーズ 2 の `Urls` と同じく、Microsoft、Xbox、Minecraft Services の各 URL を 1 つの構造体にまとめ、テストでは wiremock の URL に差し替える。

## 3. データモデル

### 3.1 マイグレーション

`0003_accounts.sql` を追加する。spec 0 の 3.4 節の accounts に、ログインし直す必要があるかどうかの列を加える。

| 列 | 内容 |
|---|---|
| id | Minecraft の UUID（主キー） |
| username | Minecraft の名前 |
| xuid | Xbox のユーザー ID。起動引数に使う |
| skin_url | 現在のスキンの画像の URL。なければ NULL |
| is_active | 使用中のアカウントか。1 件だけが 1 になる |
| added_at | 追加した日時 |
| profile_fetched_at | プロフィールを最後に取得できた日時 |
| entitlement_state | `verified`、`not_owned`、`unknown` |
| entitlement_checked_at | 所有権を最後に確認した日時 |
| verified_at | 所有権を最後に `verified` と確認できた日時。一度もなければ NULL |
| needs_login | ログインし直す必要があるか（4.5 節） |

トークンは DB に保存しない。

### 3.2 保存するもの

spec 0 の 6.3 節のとおりとする。

| 種類 | 保存先 |
|---|---|
| Microsoft の refresh token | OS の資格情報ストア。サービス名は製品版と開発版で分け（`net.ny4n.nexora` と `net.ny4n.nexora.dev`）、アカウントの UUID をキーにする |
| Microsoft、Xbox、XSTS、Minecraft のトークン | メモリだけ。それぞれの期限を別々に持つ |
| UUID、名前、XUID、スキンの URL | `accounts` テーブル |
| スキンの画像 | `cache/skins/` に、URL の SHA-256 をファイル名にして保存する |

- 資格情報ストアは `keyring-core` と、OS ごとのストアクレート（Windows：`windows-native-keyring-store`、macOS：`apple-native-keyring-store`、Linux：`zbus-secret-service-keyring-store`）を使う。Windows では Local persistence を明示する。
- 新しい refresh token の保存に成功するまで、古い refresh token は削除しない。
- 資格情報ストアへの保存に失敗した場合（使えない、上限の 2,560 バイトを超える、など）は、そのアカウントをランチャーを閉じるまでの間だけログインした状態にする。アカウント画面に「このアカウントのログインは保存されていません」と表示する。トークンの切り詰めや、平文のファイルへの退避は行わない。次にランチャーを起動したときは、`needs_login` として扱う。
- 資格情報ストアの呼び出しは、ブロックや確認のダイアログが出る可能性があるため、`spawn_blocking` の中で行う。

## 4. 認証

### 4.1 ブラウザでのログイン（主な方式）

調査 3 の 2 節と spec 0 の 6.1 節に従う。

1. `127.0.0.1` の空いているポートで待ち受ける。同じ番号のポートで `[::1]` も待ち受けられれば待ち受ける（ブラウザが `localhost` を IPv6 で解決する場合に備える）。どちらか一方からの要求を 1 回だけ受け付ける。
2. `state`（乱数）と PKCE の verifier を作り、S256 の challenge を付けた認可 URL を、`tauri-plugin-opener` でシステムブラウザに開く。`redirect_uri` は `http://localhost:<ポート>`、スコープは `XboxLive.signin offline_access`、authority は `consumers` とする。
3. 戻ってきた要求のパスが想定と違う、パラメーターが重複している、`state` が一致しない場合は、その要求を拒否する。
4. 受け付けたら、ブラウザには小さな完了のページ（外部の資源を読み込まない HTML。日本語と英語）を返し、待ち受けを閉じる。
5. コードと verifier でトークンを交換する。クライアントシークレットは使わない。
6. 待ち受けは 10 分で打ち切る。ユーザーはいつでもキャンセルできる。

コールバックの URL、認可コード、トークンは、ログに書かない。

### 4.2 デバイスコードフロー（代替の方式）

ブラウザから戻ってこない場合のために、ログイン中のダイアログに「コードを使ってログイン」を用意する。

- `devicecode` のエンドポイントに要求し、返ってきた `user_code` と `verification_uri` をダイアログに表示する。ユーザーコードはコピーできるようにする。
- 返ってきた `interval` を守ってトークンのエンドポイントに問い合わせる。`authorization_pending`、`slow_down`、`authorization_declined`、`expired_token` を扱う。
- ブラウザでのログインに切り替えたら、待ち受けは閉じる。2 つの方式を同時には待たない。

### 4.3 トークンの連鎖

spec 0 の 6.2 節と調査 3 の 3〜4 節に従う。

```
Microsoft のアクセストークン → Xbox Live ユーザートークン → XSTS（rp://api.minecraftservices.com/）
→ login_with_xbox → Minecraft のアクセストークン → 所有権の確認 → プロフィール
```

- XSTS の応答の `uhs` から identity token（`XBL3.0 x=<uhs>;<XSTS トークン>`）を作る。XUID は XSTS の `DisplayClaims.xui[0].xid` から取る。
- 各トークンの期限は、応答の値（`expires_in`、`NotAfter`）を使い、固定の時間を仮定しない。
- アカウントを追加したときと、起動の前にセッションを作り直したときに、所有権とプロフィールを確認し、`accounts` を更新する。

### 4.4 所有権の確認

- `/entitlements/mcstore` と `/entitlements/license` の両方を問い合わせる。どちらかに Java 版の項目（`product_minecraft` または `game_minecraft`）があれば `verified` とする。Game Pass の利用者は `license` の側にだけ現れると想定する。
- 空でない一覧を、それだけで所有の証拠とはしない（Bedrock 版や体験版を誤って認めないため）。
- 問い合わせが 429、5xx、タイムアウトなどで失敗した場合は `unknown` とし、所有していないとは判定しない。
- 項目の名前と Game Pass の扱いは、調査 3 で UNVERIFIED である。審査に通った後、実際のアカウントで確認し、必要なら直す（9.3 節）。

所有権の結果で、次のとおり扱いを変える（設計者の判断。Minecraft API の申請で「製品版では、ゲームを所有していないアカウントでは遊ばせない」と書いたことに合わせる）。

| 場面 | `verified` | `not_owned` | `unknown` |
|---|---|---|---|
| アカウントの追加 | 追加する | 追加しない。refresh token も保存しない。`auth.not_owned` を表示する | 追加する（`unknown` として記録する） |
| 起動 | 起動する | 起動しない（`auth.not_owned`）。Game Pass の期限切れもこれに当たる | 過去に一度でも `verified` だったアカウントは起動する。一度も `verified` になっていないアカウントは起動しない（`auth.ownership_unknown`） |

過去に `verified` だったかどうかは、`accounts` に `verified_at`（最後に `verified` になった日時）を持って判断する。

### 4.5 ログインし直す必要があるとき

次の場合に、アカウントの `needs_login` を 1 にする。

- refresh が `invalid_grant` などで拒否された（失効）
- 資格情報ストアに refresh token がない（保存に失敗したアカウントを、次の起動で読み込んだ場合など）

ネットワークに接続できない、サービスが 5xx を返す、といった一時的な失敗では、`needs_login` にしない。refresh token も削除しない。

ログインし直して成功したら、`needs_login` を 0 に戻す。ログインし直したアカウントが別のアカウント（UUID が違う）だった場合は、そのアカウントを新しく追加し、使用中にする。元のアカウントは残す。この場合は、プレイのダイアログからのログインでも自動では起動しない。ダイアログに「<名前> としてログインしました」と表示して閉じ、ユーザーがもう一度プレイを押すのを待つ。意図しないアカウントでワールドやサーバーに入るのを避けるため。

ネットワークの失敗は、次のとおり分ける。

| 失敗 | 扱い |
|---|---|
| 接続できない、タイムアウト、HTTP 5xx、HTTP 429 | 一時的な失敗。`auth.offline` とする。`needs_login` にしない。PC がオフラインの場合と、サービスの障害の場合を区別しない（どちらも、ユーザーから見れば「今は Microsoft に接続できない」ため） |
| `invalid_grant`、`interaction_required` | 失効。`needs_login` にする |
| HTTP 401（Minecraft Services） | トークンを取り直して 1 回だけやり直す。それでも 401 なら失効として扱う |
| それ以外の HTTP 4xx | 7 節のそれぞれのエラー |

### 4.6 起動の前のセッションの用意

- 起動のタスクの最初の段として「アカウントを確認中」を加え、そこでセッションを用意する。Minecraft のトークンが有効なら、そのまま使う。期限まで 5 分を切っていれば、refresh token から連鎖をやり直す。
- 同じアカウントの更新は、アカウントごとのロックで 1 件ずつ行う。
- ランチャーを起動したとき、使用中のアカウントのセッションを、裏で 1 回だけ用意しておく。これでサイドバーの状態（6.2 節）が実際に近くなり、最初の起動も速くなる。失敗しても、通知は出さない（`needs_login` の判定だけを行う）。

### 4.7 オフラインで遊ぶ

spec 0 の 6.6 節に従う。

- 「オフラインで遊ぶ」は、次の条件をすべて満たすときだけ出す：`entitlement_state` が `not_owned` でない、`verified_at` から 30 日以内、インスタンスがインストール済み、セッションの用意がネットワークの理由で失敗した。
- 30 日は定数として持ち、審査の結果などで変えられるようにする（ユーザーの判断）。Game Pass の期限が切れた後に、オフラインで無期限に遊べてしまうことを避けるため。30 日を過ぎている場合は、ダイアログに「オフラインで遊ぶには、一度オンラインで所有を確認する必要があります」と表示する。
- 起動引数には、`accounts` に保存してある UUID、名前、XUID を使う。アクセストークンには値 `0` を渡す。`user_type` は `msa` とする。この組み合わせでシングルプレイが動くことを、実機で確認する（9.3 節）。
- 失効（`needs_login`）のときは、「オフラインで遊ぶ」を出さない。spec 0 の 6.6 節が認めているのは、ネットワークに接続できない場合だけであるため。ブレインストーミングのモックアップでは、ログインし直しのダイアログにも「オフラインで遊ぶ」を置いていたが、spec 0 に合わせてこちらを優先する。

### 4.8 開発用のオフラインアカウント

- 開発ビルドでは、フェーズ 2 のオフラインアカウントを残す。アカウント画面で、Microsoft のアカウントと並べて「開発用（オフライン）」として選べるようにする。
- 開発用のオフラインアカウントは `accounts` テーブルに入れない。`app_settings` の `dev.offline_username` に加えて、`dev.offline_active`（真偽値）で使用中かどうかを持つ。`dev.offline_active` が真のときは、`accounts` の `is_active` より優先する。Microsoft のアカウントを使用中にすると、`dev.offline_active` を偽にする。このため、製品版のビルドから外すのは、`app_settings` の 2 つのキーを読む処理だけで済む。
- 製品版のビルドには、これまでどおり含めない。製品版では、ユーザー名だけのアカウントは作れない。

### 4.9 クライアント ID

- spec 0 の 6.7 節のとおり、ビルド時の環境変数 `NEXORA_MS_CLIENT_ID` で埋め込む（`option_env!`）。
- 埋め込まれていないビルドでは、ログインのボタンを押すと `auth.no_client_id` を表示する。開発ビルドでは、開発用のオフラインアカウントで引き続き起動できる。
- CI のビルドにはクライアント ID を渡さない。テストはすべて wiremock で行う。
- README に、フォークする場合は自分でクライアント ID を取得し、審査を受ける必要があることを書く。

### 4.10 アカウントの削除

- 確認のダイアログを出してから、`accounts` の行、資格情報ストアの refresh token、メモリのトークンを削除する。
- ダイアログには、「このパソコンからログインの情報を消します。Microsoft 側で発行済みのトークンが無効になるわけではありません」と表示する。
- 使用中のアカウントを削除した場合は、残りのうち最後に追加したアカウントを使用中にする。残りがなければ、使用中のアカウントはなしとする。
- そのアカウントでゲームが実行中の場合は、削除できない。

## 5. 起動の変更（M-3）

フェーズ 2 では、コマンドラインが Windows の上限（32,767 文字）を超えると、引数をすべて argfile に書いていた。このため、アクセストークンが平文で `cache/launch/<id>.args` に残っていた。次のとおり変える。

- argfile には、JVM の引数、classpath、メインクラスまでを書く。ゲームの引数（`--accessToken` を含む）は、argfile の後ろにコマンドラインで渡す。Java のランチャーは、メインクラスより後ろの引数をゲームの引数として渡す。これにより、トークンがディスクに書かれない。
- それでもコマンドラインが上限を超える場合は、`launch.command_too_long` とする。
- argfile の文字コードを、Java が argfile を読むときの文字コードに合わせる。Windows で、どの文字コードで読まれるか（Java 17 と 21 のそれぞれ）を実装の前に確認し、データフォルダのパスに日本語を含む場合に起動できることをテストと実機で確かめる。
- argfile は、ゲームが終了したとき（再起動後に終了を検出した場合を含む）に削除する。
- ゲームの出力からトークンを伏せる既存の処理（`process.rs`）は、そのまま使う。

## 6. UI

### 6.1 アカウント画面

- 追加済みのアカウントを一覧にする。各行に、スキンの顔、名前、状態（使用中、ログインが必要、ログインが保存されていない、所有を確認できない）を表示する。
- 行ごとの操作：「使う」（使用中にする）、「ログインし直す」（状態が必要なときだけ）、「削除」。
- 一覧の下に「Microsoft アカウントを追加」のボタンを置く。押すと、6.3 節のログイン中のダイアログを開く。
- アカウントが 1 件もないときは、空の状態の表示の中に、追加のボタンを置く。
- 開発ビルドでは、一覧に「開発用（オフライン）」の行を加え、名前の入力欄を残す（フェーズ 2 の表示を移す）。

### 6.2 サイドバー

- サイドバーの下部に、使用中のアカウントの顔と名前を小さく表示する。押すとアカウント画面に移る。
- 使用中のアカウントがログインし直す必要があるときは、黄色の点を付ける。ランチャーを開いただけでは、ダイアログは出さない。
- 使用中のアカウントがないときは、「ログイン」と表示する。

### 6.3 ログインのダイアログ（プレイを押したとき）

ブレインストーミングで選んだ B 案とする。

プレイを押した結果、起動のタスクが `auth.login_required` または `auth.no_account` で失敗した場合は、プレイボタンの下に失敗を表示するのではなく、画面の中央にダイアログを出す。

| 要素 | 内容 |
|---|---|
| 見出し | 「遊ぶ前にログインし直してください」（アカウントがないときは「Microsoft アカウントでログイン」） |
| アカウント | スキンの顔と名前。「ログインが終わると、そのまま起動します」 |
| 主のボタン | 「Microsoft でログインして起動」 |
| 副のボタン | なし（失効のときは「オフラインで遊ぶ」を出さない。4.7 節） |
| リンク | 「別のアカウントを使う」（アカウント画面へ）、「キャンセル」 |

- 主のボタンを押すと、同じダイアログが「ブラウザでログインしています…」の表示に変わる。この表示には、「ブラウザを開き直す」、「コードを使ってログイン」（4.2 節）、「キャンセル」を置く。
- ログインに成功したら、ダイアログを閉じ、同じインスタンスの起動を自動で始める。ただし、ログインしたアカウントが元のアカウントと違う場合は、自動では起動しない（4.5 節）。このため、ログインのタスクは、結果としてアカウントの UUID を UI に返す。
- ログインに失敗したら、ダイアログの中にエラーの文言を表示する（7 節）。
- セッションの用意がネットワークの理由で失敗した場合（`auth.offline`）も、同じダイアログを出す。このときの見出しは「Microsoft に接続できません」とし、主のボタンを「オフラインで遊ぶ」（条件を満たすとき）、副のボタンを「再試行」にする。
- アカウント画面からの追加と、ログインし直しにも、同じダイアログ（起動しない版）を使う。

### 6.4 スキンの表示

- スキンの画像は Rust で取得して `cache/skins/` に保存し、command で data URL として UI に渡す。UI は外部の URL を直接読み込まない。
- 顔は、スキンの画像の (8, 8)〜(16, 16) の範囲に、帽子のレイヤー (40, 8)〜(48, 16) を重ねて表示する。拡大はドットのまま（`image-rendering: pixelated`）にする。
- スキンの URL がない、または取得できないときは、既定の顔のアイコンを表示する。

### 6.5 command とイベント

| 種類 | 名前 |
|---|---|
| command | `list_accounts`、`set_active_account`、`remove_account`、`begin_login`（ブラウザかデバイスコードかを指定し、ログインのタスクの ID を返す）、`cancel_login`、`get_skin_face`、`launch_instance`（引数に `offline: bool` を加える） |
| イベント | `accounts-changed`、`login-progress`（ブラウザで待機中、デバイスコードの表示、Xbox の確認中、など） |

- ログインはタスクとして動かし、タスクトレイにも表示する。kind は `login` とする。
- トークンは、command の戻り値にもイベントにも含めない。

## 7. エラー

spec 0 の 11.1 節の形式に従う。文言は日本語と英語を用意する。

| コード | 場面 | 表示の方針 |
|---|---|---|
| `auth.no_account` | 使用中のアカウントがない | ログインのダイアログを出す |
| `auth.login_required` | 失効、または refresh token がない | ログインのダイアログを出す |
| `auth.offline` | Microsoft、Xbox、Minecraft に接続できない | 接続できない旨のダイアログ（6.3 節） |
| `auth.cancelled` | ユーザーがログインをキャンセルした | 何も表示しない |
| `auth.timeout` | ブラウザから 10 分戻ってこない、デバイスコードの期限切れ | もう一度試すよう案内する |
| `auth.callback_invalid` | `state` の不一致など、不正なコールバック | もう一度試すよう案内する |
| `auth.denied` | ユーザーが同意を拒否した | 何をしたら進めるかを案内する |
| `auth.xbox`（引数：xerr） | XErr が返った | 調査 3 の XErr の表に従い、番号ごとの文言を出す。知らない番号は、番号だけを表示する |
| `auth.app_not_approved` | HTTP 403「Invalid app registration」 | ランチャー側の問題（審査待ち）であり、ユーザーの問題ではないと表示する |
| `auth.not_owned` | 所有権を確認でき、Java 版がなかった | 公式の購入ページと体験版のページを案内する |
| `auth.ownership_unknown` | 所有権を確認できなかった | 時間をおいて試すよう案内する。起動は止めない（`verified` の記録があるとき） |
| `auth.no_profile` | プロフィールが 404 | 公式のランチャーか minecraft.net で、プロフィール（名前）を作るよう案内する |
| `auth.no_client_id` | クライアント ID が埋め込まれていない | 開発者向けの文言 |
| `auth.store_failed` | 資格情報ストアに保存できなかった | エラーにはしない。アカウント画面の状態として表示する |

外部のページを開くリンクは、ランチャーが持つ許可リストの URL だけにする。サーバーが返した URL をそのまま開かない。

## 8. ログと秘密情報

- トークン、認可コード、PKCE の verifier、コールバックの URL は、ログ、エラーの detail、command の戻り値、イベントに含めない。
- これらの値は `SecretString` で持つ。
- 既存の `tests/redaction.rs` に、認証の各段のエラーにトークンが含まれないことの確認を加える。

## 9. テスト

### 9.1 自動テスト

| 層 | 対象 |
|---|---|
| 単体 | PKCE の challenge（RFC 7636 の付録 B の値と一致すること）、認可 URL の組み立て、コールバックの解析（パスの違い、重複、`state` の不一致）、XErr の分類、所有権の判定、identity token の組み立て、顔の切り出しの座標 |
| 結合（wiremock） | 連鎖全体の成功、refresh、`invalid_grant` で `needs_login` になること、5xx と接続の失敗では `needs_login` にならず refresh token が残ること、403「Invalid app registration」、XErr、プロフィールの 404、所有権の各パターン、デバイスコードの各応答 |
| 結合（実際の TCP） | ループバックでの待ち受けに要求を送り、1 回だけ受け付けること、2 回目以降を拒否すること、タイムアウト、キャンセル |
| 結合 | 資格情報ストアをメモリ上の実装に差し替え、新しい token の保存に失敗したときに古い token が残ること、削除で消えること |
| 結合 | 同じアカウントの更新を同時に 2 回呼んでも、refresh が 1 回だけ行われること |
| 結合 | argfile にトークンが含まれないこと。ゲームが終了すると argfile が削除されること |
| 単体 | 「オフラインで遊ぶ」の条件（30 日の境界、`verified` でない場合、未インストールの場合）、所有権の結果ごとの追加と起動の可否 |
| UI（Vitest） | アカウント画面の状態の表示、サイドバーの黄色の点、プレイからのダイアログの出し分け（ログインが必要、接続できない、オフラインで遊べるかどうか）、ログインの成功後に起動が始まること、別のアカウントでログインしたときは起動しないこと |

CI では、実際のネットワークと実際の資格情報ストアに接続するテストを行わない。

### 9.2 審査の前にできる実機の確認

Windows で、次の手動のチェックリストを実施する。

1. ブラウザでログインし、Xbox と XSTS までが成功し、`auth.app_not_approved` の文言が表示されること
2. デバイスコードフローで同じところまで進むこと
3. ログインの途中でブラウザを閉じ、ランチャーでキャンセルできること
4. 資格情報マネージャー（Windows）に、`net.ny4n.nexora.dev` の項目が作られないこと（Minecraft まで進まないため）、または作られた場合に削除で消えること
5. データフォルダのパスに日本語を含めた状態で、argfile を使う起動ができること（開発用のオフラインアカウントで、コマンドラインを長くして確認する）
6. 開発用のオフラインアカウントで、これまでどおり起動できること

### 9.3 審査の後に行う実機の確認

1. Java 版を所有するアカウントでログインし、起動してマルチプレイのサーバーに接続できること
2. ランチャーを再起動しても、ログインし直さずに起動できること
3. 2 つ目のアカウントを追加し、切り替えて起動できること
4. ネットワークを切断した状態で、「オフラインで遊ぶ」から起動し、シングルプレイができること
5. アカウントを削除すると、資格情報マネージャーから項目が消えること
6. 所有権の項目の名前（4.4 節）が想定どおりであること。Game Pass のアカウントが手元にあれば、それでも確認する
7. スキンの顔が表示されること

審査の結果が出るまで、9.3 節は未実施のままフェーズ 3 を完了としてよい。9.3 節は、結果が出た時点で別途実施し、見つかった問題は修正の PR として扱う。
