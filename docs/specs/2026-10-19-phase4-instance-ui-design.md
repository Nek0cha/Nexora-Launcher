# フェーズ 4：インスタンス管理の UI とスキンの変更の設計

- 作成日：2026-10-19
- 状態：承認済み（2026-10-19）
- 前提：`docs/specs/2026-10-15-nexora-architecture-design.md`（spec 0）の 12 節と 13 節、`docs/specs/2026-10-16-phase3-microsoft-auth-design.md`（spec 3）
- 根拠：`docs/research/03-microsoft-auth.md`（スキンの変更の API）

## 1. 目的と範囲

フェーズ 4 の終了時点で、次のことができる状態にする。

1. インスタンス一覧の画面で、インスタンスを一覧し、作成、複製、削除、起動ができる。
2. インスタンスの詳細の画面で、名前、メモリ、Java、JVM 引数を編集できる。編集した値は、次の起動から実際に使われる。
3. ホームは「最後に遊んだインスタンスと大きなプレイボタン」だけにする。フェーズ 2 で入れた暫定のホームの選択（`HOME_SELECTION_KEY`）は取り除く。
4. アカウント画面で、Microsoft アカウントのスキンを、PNG のファイルを選んで変更できる。

### 1.1 想定する使い方

ユーザー（開発者本人）は、普段は 1〜数個のインスタンスで遊ぶ。インスタンスが数十個になる使い方は、このフェーズでは想定しない。このため、一覧には検索、並べ替え、グループ分けを設けない。素早く起動したいときは、これまでどおりホームとコマンドパレット（Ctrl+K）を使う。

### 1.2 目標でないこと（範囲外）

| 項目 | 扱うフェーズ |
|---|---|
| インスタンスのアイコン（`icon` 列は使わない） | 後で決める |
| 詳細の「コンテンツ」「ワールド」「ログ」「バックアップ」のタブ | それぞれ 5、10 など |
| ローダー（Fabric など）の選択。作成できるのは Vanilla のみ | 5 |
| メモリの自動設定（`memory_mode = auto` は固定値を使う） | 9 |
| 一覧の検索、並べ替え、グループ分け | 必要になった時点 |
| ケープの変更、スキンを元に戻す操作、スキンの履歴の保存 | 必要になった時点 |
| フェーズ 2 で後回しにした項目のうち、このフェーズと関係しないもの | 従来どおり |

### 1.3 してはいけないこと

- 起動中のインスタンスの複製と削除は、データを壊すおそれがあるため行わない。
- 名前の変更で、ゲームディレクトリを移動しない（spec 0 の `dir_name` の方針）。
- 確認なしにゲームディレクトリ（ワールドを含む）を削除しない。

## 2. インスタンスの操作（core）

`nexora-core` の `instance/` に次を追加する。変更はすべて `InstanceLocks` の中で行う。

| 操作 | 内容 |
|---|---|
| 更新 | `name`、`memory_mode`、`memory_mb`、`java_mode`、`java_path`、`jvm_args` を更新する。名前が空白だけの場合は拒否する（作成時のようにバージョン名にはしない）。起動中でも更新できる。反映は次の起動からである |
| 複製 | ゲームディレクトリを再帰的にコピーし、新しい行を作る。新しい `id` と `dir_name`（既存の `dir_name::unique` を使う）を割り当て、`last_played_at` は空、`play_time_ms` は 0 にする。名前と設定、`mc_version`、`state` は元から引き継ぐ。ワールドを含むため時間がかかりうる。タスク管理（`task/`）に載せて進捗を出す |
| 削除 | ゲームディレクトリを削除してから、行を削除する。ディレクトリの削除に失敗した場合は行を残し、エラーを返す |

- 複製と削除は、対象が起動中（`running_sessions` に行がある）か、`state` が `installing` の場合は拒否する。拒否の理由は、画面に出せるエラーとして返す。
- 複製した直後にコピーが途中で失敗した場合は、作りかけのディレクトリと行を残さない。
- 削除したインスタンスの共有ファイル（`shared/` のライブラリやアセット）は消さない。

### 2.1 起動への反映

現在の起動処理は、メモリを固定値（`launcher.rs` の `MEMORY_MB`）で渡しており、`memory_*`、`java_*`、`jvm_args` の列を読んでいない。次のように読むようにする。

| 設定 | 動作 |
|---|---|
| メモリ：自動 | これまでの固定値を使う |
| メモリ：手動 | `memory_mb` を `-Xmx` に使う。下限と上限は builder が決める（下限は 512 MB 程度、上限は実メモリの範囲内を想定） |
| Java：自動 | これまでどおり、Mojang の Java を使う |
| Java：手動 | `java_path` の実行ファイルを使う。存在しなければ、起動前にエラーにする |
| JVM 引数 | 空白で区切り、二重引用符で囲んだ部分は 1 つの引数として扱う。`-Xmx` は `memory_*` の設定と競合するため、JVM 引数に `-Xmx` が含まれていれば、画面で警告し、起動ではその `-Xmx` を無視してメモリの設定の値を使う — ここは私の判断である |

- argfile と @argfile の扱い（フェーズ 3 の M-3）を変えない。JVM 引数は、これまでの引数と同じ経路で渡す。

## 3. 画面

### 3.1 インスタンス一覧（`/instances`）

- 1 件を 1 行で表示する：名前、バージョン、状態（準備中、使用可能、壊れている）、最後に遊んだ日時、プレイ時間。
- 行の操作：プレイボタン（既存の `PlayButton`）、詳細を開く、複製、削除。複製と削除はメニューにまとめる。
- 画面の上部に、インスタンスの作成（既存の `CreateInstanceDialog`）を置く。
- 並び順はバックエンドの順（最後に遊んだ順、なければ作成の新しい順）のままとする。
- インスタンスが 0 件のときは、既存の空の状態の表示から作成のダイアログを開けるようにする。
- 削除は確認のダイアログを出す。ダイアログには、インスタンスの名前と「ワールドを含むすべてのデータが削除され、元に戻せない」ことを書く。標準の操作は「キャンセル」とする。
- 複製中は、その行に進捗を出し、完了するまでその行の複製、削除、起動を無効にする。

### 3.2 インスタンスの詳細（`/instances/:id`）

- 見出しにインスタンスの名前とバージョンを出し、一覧に戻る手段を置く。
- このフェーズのタブは「設定」だけとする。他のタブは、中身ができるまで表示しない（空のタブを並べない）— 私の判断である。
- 設定のフォーム：名前、メモリ（自動／手動と MB）、Java（自動／手動とパス）、JVM 引数。
- 保存は、フォームの下の「保存」ボタンで行う。変更がないときはボタンを無効にする。保存に失敗したら、既存の `FailureNotice` で理由を出す。
- 起動中のインスタンスを開いたときは、「設定は次の起動から反映される」と表示する。
- 存在しない `id` に来たら、一覧へ戻す案内を出す。
- Java のパスは、テキスト入力とする（ファイル選択ダイアログは使わない。後述の 4 節の判断と同様に、新しいプラグインを増やさないため）— 私の判断である。

### 3.3 ホーム

- 表示するのは、一覧の先頭のインスタンス（最後に遊んだもの、なければ作成の新しい順で先頭のもの）と、プレイボタンである。
- `HOME_SELECTION_KEY`、`setHomeSelection`、`pickHomeInstance`、`useHomeInstance` の選択の仕組みを取り除き、`useHomeInstance` は先頭を返すだけにする。関連するテスト（`HomeSelection.test.tsx`）も整理する。
- ホームの見出しの横にある作成ボタンは取り除く。インスタンスが 0 件のときの空の状態の作成ボタンは残す。インスタンスの作成は一覧の画面に集約する。
- 作成が終わった後は、一覧の画面にとどまる（作成したインスタンスが一覧に現れ、そこから起動できる）。

### 3.4 コマンドパレット

- 既存の「インスタンスを起動」の項目はそのまま使う。「インスタンスを開く」の項目を追加するかどうかは builder が決める。

## 4. スキンの変更

### 4.1 操作

- アカウント画面の Microsoft アカウントの行（またはスキンの表示の近く）に「スキンを変更」を置く。
- 押すと、PNG のファイルを選ぶ。ファイルの選択には HTML の `<input type="file" accept="image/png">` を使い、読み込んだバイト列を IPC で core に渡す（`tauri-plugin-dialog` は追加しない）— 私の判断である。
- モデル（Classic／Slim）を選べるようにする。初期値は、現在のスキンのモデルとする（プロフィールから取得できない場合は Classic）。
- 送信の前に、PNG のシグネチャと寸法（64×64 または 64×32）を core で検証し、合わなければ送信せずにエラーにする。サイズの上限は調査 3 に従う。
- 成功したら、アカウントの一覧とサイドバーのスキンの顔を更新する（キャッシュの `cache/skins/` は URL のハッシュで管理しているため、新しい URL を取り直せば古い画像は使われない）。

### 4.2 core

- `auth/minecraft.rs` に、Minecraft Services のスキンの変更の API を呼ぶ関数を追加する（`POST /minecraft/profile/skins`、`variant` と画像のマルチパート）。トークンは `AuthService` が持つ有効なアクセストークンを使い、期限切れなら既存の更新の経路で取り直す。
- 429（レート制限）や 401 など、失敗の種類を既存の `CoreError` に載せて、画面に理由を出せるようにする。
- 開発用のオフラインアカウントには、スキンの変更を出さない。
- 実際の API の挙動は、Minecraft API の審査を通ったアプリでのみ確認できる。審査は通っている（2026-10-17）。

## 5. 構成

| 層 | 変更 |
|---|---|
| core | `instance/`（更新、複製、削除）、`launcher.rs` と `launch/`（設定の反映）、`auth/minecraft.rs` と `auth/service.rs`（スキンの変更） |
| src-tauri | コマンドの追加：インスタンスの更新、複製、削除、スキンの変更。複製の進捗は既存のタスクのイベントを使う |
| ui | `routes/Instances.tsx`、新規の `routes/InstanceDetail.tsx`、`routes/Home.tsx`、`routes/Accounts.tsx`、`features/instances/`、`api/commands.ts`、i18n（ja、en）、ts-rs の bindings |

- DB のマイグレーションは不要である（必要な列は `0002_instances.sql` に揃っている）。必要になった場合は builder が追加してよい。
- UI の文言は、日本語と英語の両方に追加する。

## 6. テストと確認

- core：更新、複製、削除、起動中の拒否、複製の失敗時の後始末を、単体のテストで確認する。設定の反映（`-Xmx`、Java のパス、JVM 引数の分割）は、既存の `launch/args.rs` のスナップショットのテストに合わせる。
- UI：一覧の操作（複製、削除の確認）、詳細のフォームの保存、ホームの表示、スキンの変更のダイアログを、既存の Vitest のテストの書き方に合わせて確認する。
- CI：3 つの OS で通ること。
- 手動の確認（実機）：
  1. インスタンスを作成し、複製し、複製の側で起動できる。
  2. メモリを手動にして起動し、`-Xmx` が反映されている。
  3. 起動中のインスタンスの複製と削除が拒否される。
  4. 削除でゲームディレクトリが消え、`shared/` は残る。
  5. スキンを変更し、アカウントの一覧とサイドバーの顔が更新される。ゲームの中でも新しいスキンが見える。

## 7. builder に任せること

- コマンドとイベントの名前、モジュール内の分け方。
- 一覧の行の見た目、メニューの出し方、複製中の進捗の見せ方（デザインの原則は spec 0 の 12 節に従う）。
- メモリの下限と上限、スキンの画像のサイズの上限の具体的な値。
- 複製のコピーを、ファイルごとに進捗を出す形にするか、全体で出す形にするか。

## 8. 実装での判断

実装で、この設計を具体化した点、または変えた点を記す。

- 複製と削除を断る条件は、インスタンスが起動中であるか、インストールか起動のタスクで終了していないものがあることだけである。`state` が `installing` であることだけでは断らない。アプリが強制終了されて `installing` のまま残った行も、削除と複製ができる。複製の行はコピーの間 `installing` で置き、コピーを終えてから元の `state` にする（途中でアプリが落ちた複製を使える状態に見せないため）。
- 複製のコピーが失敗または取り消しになった場合は、コピー先のディレクトリと新しい行を消す。ディレクトリを消せなかった場合は、行を残して `broken` にする。一覧に出るので、利用者が削除できる。
- スキンの変更では、取り直したプロフィールから `accounts` の `name`、`skin_url`、`profile_fetched_at` だけを更新する。所有権の `verified_at` と `entitlement_checked_at` は動かさない。
- 利用者の JVM 引数は、`${...}` の置換をしない。`-Xmx` の直後、バージョン自身の JVM 引数の前に入れる。引数の中の `-Xmx` は無視し（UI で警告する）、メモリの設定の値だけを使う。
- 手動の Java は、Mojang が要求する major と合うかを確かめない。存在するファイルかだけを確かめる。UI では、パスの前後の空白と、前後を囲む引用符を取り除いて保存する。
- 複製のインスタンスの名前は、元と同じにする（`dir_name` は重複しないものにする）。
