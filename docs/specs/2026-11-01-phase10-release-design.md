# フェーズ 10 公開と自己更新 設計

全体設計（`2026-10-15-nexora-architecture-design.md`）を補う spec である。食い違う場合は、この文書を優先する。

## 1. 目的と方針

- 1 週間以内（2026-11-08 まで）に、Windows、macOS、Linux 向けの配布物を GitHub Releases で公開する。
- 公開後は、利用者がアプリの中から新しい版へ更新できるようにする。
- お金をかけない。Windows と macOS のコード署名は行わず、初回の警告は README で案内する（利用者が決めた）。
- 公開に必要なものを先に作る。バックアップの UI と CurseForge のキーは公開後に回す（2.2 節）。

## 2. 範囲

### 2.1 含めるもの

1. 配布物の作成：タグの push で、3 つの OS のインストーラと更新用のファイルを GitHub Releases に出す。
2. 自己更新：起動時の更新確認、設定画面からの手動の確認、利用者の操作によるダウンロードと再起動。
3. ライセンス表示：バージョン、ライセンス、リポジトリへのリンク、第三者のライセンス文を見られる画面。
4. OSS としての公開：README の整備（導入方法、警告の開き方、既知の制約）。

### 2.2 含めないもの

- バックアップの UI。更新前とバージョン上げ前の自動バックアップは既にあり、足りないのは「戻す画面」だけである。利用者が使うか分からないため、公開後の要望を見て決める（利用者が決めた）。
- CurseForge の API キーと CurseForge 連携（将来の機能。利用者が決めた）。
- Windows と macOS のコード署名と公証。
- deb や rpm の自動更新（Linux で自動更新できるのは AppImage だけにする）。
- 更新の自動インストール。必ず利用者の操作を挟む。
- 更新の差分配信、ベータ版の配信経路、更新内容（リリースノート）の画面内の整形表示。
- Issue テンプレート、CONTRIBUTING などのコミュニティ向けファイル。

## 3. 配布物

| OS | 形式 | 自動更新 |
|---|---|---|
| Windows | NSIS のインストーラ（`.exe`） | する |
| macOS | `.dmg`（Apple Silicon と Intel の 2 つ）。更新用に `.app.tar.gz` | する |
| Linux | AppImage、deb | AppImage のみ |

- `tauri.conf.json` の `bundle.targets` は `"all"` から、上の形式に絞る。
- macOS は署名なしで出す。Apple Silicon で起動できるよう、ad-hoc 署名（`signingIdentity: "-"`）を使う（実装者の判断）。
- 版番号は `0.1.0` から始める。正式版（pre-release ではない）として出す。更新確認は pre-release を見ないため、pre-release にすると更新が届かない（実装者の判断）。
- 版番号は `tauri.conf.json`、`Cargo.toml`（workspace）、タグの 3 か所で一致させる。リリースの流れの中で食い違いを検出する。

## 4. 配布の自動化（GitHub Actions）

- `v*` のタグの push で動く `release.yml` を足す。CI（`ci.yml`）とは別にする。
- 3 つの OS（macOS は 2 つのアーキテクチャ）で `tauri-apps/tauri-action` を使い、下書きのリリースに配布物と `latest.json` を添付する。公開は人が下書きを確認して押す（実装者の判断）。
- 更新用の署名鍵（minisign）を `tauri signer generate` で作る。秘密鍵とパスワードは GitHub の Secrets（`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）に置き、公開鍵は `tauri.conf.json` に書く。秘密鍵をリポジトリに入れない。
- `NEXORA_MS_CLIENT_ID`（Microsoft サインインのクライアント ID）を、リリースのビルドに渡す。公開クライアントで秘密ではないが、リポジトリの変数（Variables）に置く（実装者の判断）。
- 秘密鍵を失うと、既存の利用者に更新を届けられなくなる。鍵の控えを保管する手順を README ではなく開発者向けの文書に書く。

## 5. 自己更新

### 5.1 仕組み

- Tauri の updater プラグインを使う。更新の情報は `https://github.com/Nek0cha/Nexora-Launcher/releases/latest/download/latest.json` から取る。
- 更新の検証は、署名（minisign）と公開鍵で行う。OS のコード署名とは無関係である。

### 5.2 利用者から見た流れ

1. 起動したあと、1 度だけ更新を確認する（バックグラウンド。失敗しても何も出さない）。
2. 新しい版があるとき、ヘッダーに「更新あり」の印を出す。押すと、新しい版の番号と、「更新して再起動」のボタンを出す。
3. 「更新して再起動」で、ダウンロード（進捗を表示）、インストール、再起動をする。
4. 設定画面に、現在の版と「更新を確認」のボタンを置く。確認の結果が「最新」なら、そう表示する。確認が失敗したときは、失敗したと表示する。
5. ゲームの起動中は、「更新して再起動」を押せない状態にする。更新のダウンロード中に失敗したときは、トーストで知らせ、現在の版のまま使い続けられる（実装者の判断）。

UI の文言に説明文を足さない（既存の方針どおり、配置と形で伝える）。日本語の文言は「バージョン」を使う（「版」と書かない。既存のテストが検査している）。

### 5.3 未確認の事項

- macOS で署名なしのアプリが、updater で置き換えられるか。実機での確認が要る。
- Linux の AppImage 以外（deb）で、更新の確認だけが出て適用できない状態にならないか。deb では更新の印を出さない扱いにするのが安全だが、判別の方法は実装時に確かめる。
- 更新の動作そのものは、2 つ目の版（`0.1.1`）を出すまで、実際には確かめられない。0.1.0 の公開後に 0.1.1 を出して確かめることを、この段階の完了条件に含める。

## 6. ライセンス表示

- 設定画面に「このアプリについて」の項目を置く：バージョン、ライセンス（Apache-2.0）、リポジトリへのリンク、第三者のライセンスの一覧。
- 第三者のライセンスは、Rust の依存とフロントエンドの依存の両方を含める。生成の道具（`cargo-about` など）の選び方と、生成物を配布物に同梱して画面から読む方法は、実装者に任せる。生成はリリースの流れの中で行い、手書きの `THIRD_PARTY_NOTICES.md` は置き換える。
- 配布物に `LICENSE` を同梱する。

## 7. OSS としての公開

- README を、公開向けに更新する。英語を主とし、日本語の節は残す。
  - 導入方法（OS ごとのダウンロード先）。
  - Windows の SmartScreen の警告の開き方、macOS の「システム設定 → プライバシーとセキュリティ → このまま開く」の手順。署名しない理由を一文で添える。
  - 実機での確認が済んでいない機能（Forge と NeoForge、Prism Launcher などからの取り込み）の明記（既存の記述を保つ）。
  - 「Windows が最初の対象」とある記述を、3 つの OS を配布することに合わせて直す。
- リポジトリは既に公開されている（利用者に確認済み）。公開の切り替えは要らない。

## 8. 完了条件

1. タグの push で、3 つの OS の配布物が下書きのリリースに揃う。
2. 各 OS の配布物から、アプリを導入して起動できる（実機で確かめられる範囲。確かめられない OS は未確認と書く）。
3. `0.1.0` を公開し、`0.1.1` を出して、アプリ内の更新が動くことを確かめる（確かめられない OS は未確認と書く）。
4. 設定画面に「このアプリについて」があり、第三者のライセンスを読める。
5. README が 7 節の内容を満たす。

## 9. 実装者に任せること

- Tauri の updater プラグインの設定の細部、権限（`capabilities`）の足し方。
- 更新の印と更新のダイアログの見た目（既存のヘッダー、ダイアログの部品に合わせる）。
- ライセンス一覧の生成方法と表示方法。
- 版番号の一致を検出する方法。
