# インスタンスのバージョンアップグレード 設計

全体設計（`2026-10-15-nexora-architecture-design.md`）を補う spec である。食い違う場合は、この文書を優先する。

## 1. 目的と方針

- 既存のインスタンスの Minecraft バージョンを、ワールド・設定・MOD を保ったまま新しいバージョンに上げられるようにする。「1.20.1 で遊んでいたワールドを 1.21 で続けたい」という場面が主である。
- ワールド、設定（`options.txt`、`config/` など）、MOD のファイルには触れない。MOD を自動で消したり入れ替えたりしない。
- 上げる前に、新しいバージョンで困りそうな MOD を知らせる。上げてから起動して落ちて初めて気づく流れにしない。
- 途中で失敗・キャンセルしたとき、元のバージョンで遊べる状態に戻す。

## 2. 範囲

### 2.1 含めるもの

- Minecraft バージョンの引き上げ（現在より新しい正式版）。
- ローダー（Fabric、Quilt、NeoForge、Forge）付きのインスタンスでは、同じ種類のローダーを新しい Minecraft 用の版に合わせて引き上げる。
- 上げる前の確認：MOD ごとの対応状況（2.3 節）の一覧。
- 上げる前のワールドの退避（4.4 節）。

### 2.2 含めないもの

- 古いバージョンへ下げる操作。
- ローダーの種類の変更（Fabric から Forge など）、Vanilla へのローダー追加。
- MOD の自動更新・自動削除。上げたあとの更新は、既存の「更新を確認」「すべて更新」を使う。上げたあとはインスタンスのバージョンが新しくなっているので、その確認は新しいバージョンに対して行われる（既存の動作、`content/updates.rs`）。
- リソースパック、シェーダーの対応確認。
- ワールドの変換。ワールドは新しい Minecraft が開いたときに自動で更新する（Minecraft 側の仕様）。

### 2.3 MOD の対応状況

確認画面で、MOD を 3 つに分けて見せる。

| 区分 | 意味 |
|---|---|
| 対応あり | Modrinth に、新しいバージョンとローダーに合う版がある |
| 対応なし | Modrinth の MOD だが、合う版が見つからない |
| 確認できない | Modrinth で特定できなかった MOD（ローカルの jar など）と、版を固定してある MOD。対応の有無を調べられない |

無効にしてある MOD も同じ基準で数える。対象は MOD だけで、リソースパック、シェーダー、データパックは数えない。

「対応あり」でも、入っている jar は古い版のままである。入れ替えは上げたあとに利用者が既存の更新機能で行う。確認画面の目的は、上げるかどうかの判断材料を出すことであり、「対応なし」と「確認できない」の件数と一覧が中心になる。

## 3. 利用者から見た流れ

1. インスタンスの画面から「バージョンを上げる」を開く。
2. 上げ先の Minecraft バージョンを選ぶ（現在より新しい正式版のうち、このインスタンスのローダーに対応するものだけを並べる。スナップショットは出さない）。
3. ローダー付きなら、ローダーの版は自動で決める（5 節）。決められなければ、その旨を示して先へ進めない。
4. MOD の対応状況の確認が出る。確認中は読み込み表示を出す。通信できなければ、確認できないことを示し、それでも続けるか選べる。
5. 「上げる」で実行する。進捗は既存のタスク表示に出る。
6. 完了すると、インスタンスのバージョン表示が新しくなる。

画面に説明文は足さない。件数のバッジ、アイコン、一覧の並びで伝える（既存の UI 方針）。日本語の表記は「バージョン」を使い、「版」と書かない（既存のテストが守っている）。

## 4. 動作

### 4.1 コア API

- `preview_upgrade(instance_id, target_mc_version) -> UpgradePreview`：上げ先で使うローダー版（あれば）と、MOD の 3 区分の一覧を返す。インスタンスは変更しない。
- `upgrade_instance(instance_id, target_mc_version) -> task_id`：タスク（種別 `instance-upgrade`）を始める。同じインスタンスにインストール、起動、中身、取り込みのタスクが動いている間は `InstanceBusy`。起動中のゲームがあれば拒否する（既存の `ensure_idle` と同じ扱い）。

### 4.2 MOD の確認

既存の `content::updates::check` が、`(rows, mc_version, loaders)` を引数に Modrinth へハッシュで一括問い合わせする。これに上げ先の Minecraft バージョンを渡して再利用する。`check` の戻り値は、上げ先に合う版がある MOD を `updates`（入っている版と別の版）に入れ、入っている版がそのまま合う MOD はどちらにも入れず、Modrinth 由来で合う版が無い MOD を `no_compatible` に入れる。版を固定した MOD と、ハッシュの無い行は `check` が対象にしない。分類は次のとおり：`no_compatible` は「対応なし」、対象の Modrinth の MOD のうち `no_compatible` でないものは「対応あり」、それ以外（Modrinth 由来でない、版を固定した、ハッシュが無い）は「確認できない」。確認の結果は上げ先のバージョンに対するものなので、既存の 15 分のキャッシュには入れない。

### 4.3 実行

タスクはインスタンスのロックを取って動かす（取り込みと同じ）。

1. ワールドを退避する（4.4 節）。
2. 元の `mc_version`、`loader_version`、`state` を保持する。
3. インスタンスの行を上げ先に更新し、`state` を `installing` にする。
4. 既存の `install()` を実行する。これは行のバージョンから、クライアント、ライブラリ、アセット、ローダーのプロファイル、Java を揃える。確認したところ、`install()` はファイルを足すだけで、古いバージョンのファイルを消したり上書きしたりしない（クライアント、ライブラリ、アセット、固定したローダーのプロファイルはバージョンごとの共有の場所に置かれる）。
5. 成功したら `ready` にして、MOD の対応確認のキャッシュを捨てる（`UpdateCache::invalidate`）。
6. 失敗かキャンセルなら、手順 2 で保持した値に行を戻す。`install()` は失敗で `broken`、キャンセルで `installing` を書くので、`state` も手順 2 の値で上書きする。古いバージョンのファイルは残っているので、そのまま遊べる。

手順 3 と 6 の間にアプリが落ちた場合、元の値は残らず、行は上げ先のバージョンで `installing` のまま残る。次に Play を押すと既存の動作で `install()` が再開される。上げ先の導入が失敗し続ける場合は、そのバージョンのまま直せない（下げる操作は含めない）。この窓は狭いので、元の値を保存する仕組みは作らない。ワールドは退避と元のフォルダーに残っている。取り込みのように行を消すことはしない（利用者のデータが入っているため）。

### 4.4 ワールドの退避

- 上げる前に `saves/` を `backups/<instance_id>/upgrade-<時刻>/saves` にコピーする。コピーは既存の `import::copy::copy_tree`（リンクをたどらない。キャンセルと進捗に対応している）を使い、進捗はタスクに出す。
- 残すのは最新の 1 件。新しい退避が最後まで終わってから古い退避を消す。
- 退避に失敗かキャンセルされたら、途中の退避を消し、上げる操作を始めない。空き容量の事前確認はしない（コピーの失敗で止まる）。
- 退避を作る/作らないの切り替えは設けない（常に作る）。ワールドは新しい Minecraft で一度開くと古いバージョンで開けなくなることがあるため。

## 5. ローダーの版の決め方

- Vanilla：なし。
- それ以外：同じ種類のローダーについて、上げ先の Minecraft 用に出ている版のうち、最新の安定版を使う（既存の `latest_stable`）。出ている版が無ければ、`preview_upgrade` がその旨を返し、上げられない。
- 現在のローダー版を保つことは試みない（Minecraft 用に作られた別の版が必要になるため）。

## 6. 失敗

- 通信できずに MOD の確認ができない：確認できないことを示し、続けるかを利用者が選ぶ。続けた場合、実行（4.3 節）自体も通信が必要なので、そこで失敗すれば元に戻る。
- 上げ先のバージョンやローダー版が取得できない：`install()` の既存のエラー。元に戻る。
- 手動指定の Java が上げ先に合わない（例：Minecraft 1.20.5 以降は Java 21）：自動の場合は `install()` が合う Java を選ぶ。手動指定で合わなければ、既存の起動時のエラーと同じ扱いにする（ここでは追加の対応をしない）。

## 7. 構成

- `crates/nexora-core/src/launcher/upgrade.rs`：`preview_upgrade`、`upgrade_instance`、`UPGRADE_KIND`。
- `crates/nexora-core/src/instance/mod.rs`：行の `mc_version` と `loader_version` を更新する関数（元に戻すためにも使う）。
- Tauri コマンド `preview_upgrade`、`upgrade_instance`。
- UI：`ui/src/features/upgrade/`。インスタンスの画面から開くダイアログ。ヘッダーの配置は既存のレイアウトに合わせる。
- 既存のタスク一覧への表示、`active_task_with_kind` の対象に `UPGRADE_KIND` を足す（他の操作を `InstanceBusy` にするため）。

## 8. テスト

- コア：Fake の Mojang/Modrinth を使った統合テスト。上げて成功し `mc_version`、`state`、ワールドの退避を確かめる／失敗とキャンセルで行が元に戻る／ローダー版が無いと拒否する／MOD の 3 区分／退避の失敗で何も変えない／タスク中の拒否。
- UI：バージョンの並び（現在より新しい正式版だけ）、3 区分の表示、通信できないときの表示。

## 9. 利用者が決めたことと、実装側の判断

利用者が決めたこと：ワールド、設定、MOD はそのまま残す／対応のない MOD は上げる前に知らせてほしい／「1.20.1 から 1.21 へ」のような引き上げが主な場面。

実装側の判断（利用者に確認していない）：下げる操作を含めない／ローダーの版は最新の安定版／ワールドの退避を常に取り、最新の 1 件だけ残す／空き容量の事前確認はしない／確認の結果をキャッシュしない／確認と実行の間に MOD が変わっても確認は更新しない（確認は判断材料であり、実行を縛らない）／途中で落ちたときは元の値を保存せず続きから完了させる／スナップショットを選べなくする／選べるバージョンをローダー対応のあるものに絞る（`game_versions`）／ほかの設定（Java、メモリ）には手を付けない。

## 10. 実装者に任せること

- ダイアログの見た目と文言（既存の画面の流儀に合わせる）。
- 退避の時刻の表記、フォルダー名の細部。
- 確認の問い合わせの並列度、タイムアウト。
