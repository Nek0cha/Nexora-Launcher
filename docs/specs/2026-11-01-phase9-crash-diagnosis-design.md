# フェーズ 9 クラッシュ診断と既定メモリ 設計

全体設計（`2026-10-15-nexora-architecture-design.md`）を補う spec である。食い違う場合は、この文書を優先する。

## 1. 目的と方針

- ゲームが異常終了したとき、原因になった MOD を特定し、その場で無効化できるようにする。MOD が増えるほど、ログを読んでも原因にたどり着けず、手作業で MOD を外して探すことになる。この手間を減らすのが主目的である。
- 原因を断定できないときも、落ちたことを知らせ、ログを開けるようにする。何も出さずに終わらせない。
- 無効化は利用者が選んだものだけに行う。MOD を自動で無効化・削除しない。
- あわせて、「自動」のメモリ値を全体設定で変えられるようにする（9 節）。

## 2. 範囲

### 2.1 含めるもの

- 異常終了の直後に、ゲームのログとクラッシュレポートを読む診断。
- 原因の候補の MOD の一覧と、選んだ MOD の無効化。
- 原因が分からないときの、ログを開く案内。
- 「自動」のメモリ値を全体設定で変える項目。

### 2.2 含めないもの

- メモリの自動算出（物理メモリや MOD の数から決める式）。全体設計 5.5 節の想定は取りやめる。
- 環境レシピ（`.mrpack` に独自の設定を足した形式）。取りやめる。書き出しと取り込みは、フェーズ 7 の `.mrpack` のままとする。
- クラッシュレポートの送信、共有、診断結果の保存。
- JVM 自体の異常終了（`hs_err_pid*.log`）の解析。この場合は原因を特定せず、ログを開く案内のみとする。
- 無効化したあとの再起動、MOD の更新・入れ替えの提案。
- 診断の精度を上げるための、利用者へのファイルの提出の依頼。

全体設計のフェーズ表（13 節）と未決定の事項（14 節）は、この文書の内容に合わせて、実装時に書き換える（フェーズ 9 を「クラッシュ診断、既定メモリ」とし、「環境レシピの形式」の行を削る）。

## 3. 利用者から見た流れ

1. ゲームが異常終了する（終了コードが 0 でない）。
2. ランチャーが終了の直後に診断を行い、ダイアログを出す。
3. 原因の候補が見つかったとき：候補の MOD を一覧で見せる。最初は確度が高い候補すべてにチェックが入っている。確度が低い候補（`StackTrace` だけが手がかりのもの）は、最初はチェックを外しておく（利用者が決めた）。利用者がチェックを外し、「無効化」を押すと、チェックの付いた MOD だけを無効化する。「閉じる」で何もせず閉じる。
4. 候補が見つからないとき：「落ちました」と知らせ、「ログを開く」を出す。
5. どちらのダイアログにも「ログを開く」を置く。押すと、そのインスタンスのログ画面を、今回の起動のログで開く。

出さない場合：終了コードが 0 のとき（普通にゲームを閉じたとき）。終了コードが分からないとき（ランチャーを閉じている間に終わったゲームを、再起動後に引き継いだ場合）。ランチャーの操作でゲームを止めたとき（その操作がある場合。実装時に確かめる）。それ以外の非 0 は、利用者が OS から強制終了した場合も含めて診断する（実装者の判断で決めた方針）。強制終了では手がかりが見つからず、「候補なし」のダイアログになる。

画面に説明文は足さない。MOD の並び、アイコン、理由のラベルで伝える（既存の UI 方針）。日本語の表記は「バージョン」を使い、「版」と書かない（既存のテストが守っている）。

## 4. 診断

### 4.1 入力

「今回の起動」は、起動時刻（`launched_at`、ミリ秒）で特定する。ランチャーは起動時にこの値を持っており（`launch/process.rs` の起動情報）、ゲームログのファイル名もこの値である。終了の通知とあわせて、診断にこの値を渡す（実装者の判断で決めた方針）。

- 今回の起動のゲームログ（ランチャーが保存している `logs/game/<id>/<起動時刻>.log`、`instance/logs.rs`）。読むのは末尾の `MAX_READ_BYTES` までとする。
- 今回の起動の開始時刻以降に更新された `crash-reports/` のファイルのうち、最も新しい 1 つ。なければ使わない。
- 有効な MOD の一覧（`content` の行）と、各 jar の MOD ID の対応（4.3 節）。

起動の途中で落ちるとクラッシュレポートが作られないことがあるため、ゲームログだけでも診断できなければならない（利用者の話では、起動の途中で落ちる場合が多い）。

### 4.2 原因の見つけ方

入力から、次の種類の手がかりを探す。それぞれ、MOD ID（または jar のファイル名）を取り出す。

| 理由のコード | 手がかり |
|---|---|
| `MissingDependency` | 必要な MOD が入っていない、という読み込みエラー。原因として挙げるのは、必要としている側の MOD である |
| `IncompatibleVersion` | 必要な MOD のバージョンが合わない、という読み込みエラー。挙げるのは、必要としている側の MOD である |
| `ModLoadingError` | 特定の MOD の読み込みに失敗した、というローダーのエラー（初期化、重複、ローダー違いなど） |
| `MixinFailure` | Mixin の適用に失敗した、というエラー。どの MOD の Mixin 設定かを取り出す |
| `SuspectedInReport` | クラッシュレポートに、疑わしい MOD として書かれているもの |
| `StackTrace` | スタックトレースのクラスが、特定の MOD の jar にだけあるもの。確度は低い |

- 確度は「高い」（上の `StackTrace` 以外）と「低い」（`StackTrace`）に分ける。
- 同じ MOD に複数の手がかりがあれば、理由を全部持たせ、一覧には 1 行で出す。
- 一覧は、確度が高いものを先に、その中は理由の強さ（`MissingDependency`、`IncompatibleVersion`、`ModLoadingError`、`MixinFailure`、`SuspectedInReport` の順）で並べる。
- ローダー（Fabric、Quilt、Forge、NeoForge）ごとに、エラーの書式が違う。各ローダーの書式は、実装前に調査資料（`docs/research/`）にまとめ、そこにある書式だけを扱う。**この文書の作成時点では、書式は公開されている情報にもとづく想定であり、実機では未確認である。** 確認は実装時のテストと実機確認で行う（10 節）。
- 手がかりから取り出した ID に対応する MOD が見つからない場合（入っていない MOD、ランチャー管理外の jar など）は、その候補を一覧に出さない。`MissingDependency` で「入っていない側」の MOD は、一覧の候補にせず、理由の中の名前として見せる。

### 4.3 MOD ID と jar の対応

- 各 MOD の jar から、MOD ID を読む（Fabric / Quilt の `fabric.mod.json` / `quilt.mod.json`、Forge / NeoForge の `mods.toml`、旧 Forge の `mcmod.info`）。アイコンや名前の読み取り（`content/local_meta.rs`、`content/identify.rs`）がすでに同じファイルを読んでいる。再利用できるか、実装時に確かめる。
- 有効な MOD だけを対象にする。すでに無効の MOD は候補にしない。
- jar に複数の MOD ID が入っている場合（同梱された MOD）は、外側の jar を無効化の対象にする。

### 4.4 失敗しても止めない

診断はベストエフォートである。読み取りや解析に失敗しても、ゲームの終了処理（プレイ時間、後始末、終了の通知）を妨げない。失敗したときは、「候補なし」と同じ扱い（4 節の流れの 4）にする。

## 5. 無効化

- 選んだ MOD ごとに、既存の `content::ops::set_enabled`（`.disabled` の付け外し）で無効化する。MOD のファイルの中身には触れない。
- 一部が失敗したときは、成功した分は無効化のままにし、失敗した MOD とその理由を一覧で見せる。
- 元に戻すには、既存の MOD 一覧から有効にする。このダイアログに「元に戻す」は置かない。
- 起動中のゲームがあるインスタンスでは行わない（異常終了の直後なので、通常は起きない）。

## 6. コア API と画面

- 診断はコア（`nexora-core`）に置く。入力はインスタンス ID と、今回の起動を特定する情報で、出力は次のとおり。
  - 候補の一覧：MOD のファイルの相対パス、表示名、MOD ID、理由のコード（複数）、確度、手がかりの行（根拠として見せる短い抜粋）。
  - 使ったログの名前（ログ画面を開くため）。
- 診断を呼ぶ契機：ゲーム終了のイベント（`GAME_EXITED`）を受けた画面が、終了コードが 0 でなければ診断を呼ぶ。診断を `finish` の中で行って結果を終了イベントに載せるか、画面からコマンドで呼ぶかは、実装時に決める（どちらでも 4.4 節を守ること）。
- 理由のコードは UI で日本語にする。コードがすべて訳されていることを確かめるテストを置く（インポートの `Unsupported` と同じ方法）。
- 終了後の同期の提案（`sync::proposals::collect_proposals`）も同じ終了の直後に出る。両方が出る場合は、クラッシュのダイアログを先に出し、閉じてから同期の提案を出す（順に出す。実装者の判断で決めた方針）。既存の画面の構造で順に出せない場合は、実装時に相談する。

## 7. 保存しないもの

診断の結果は保存しない。ダイアログを閉じたら、同じ結果は再び出ない。あとで調べるときは、ログ画面を使う。

## 8. エラー

診断自体のエラー（ファイルが読めないなど）は、利用者にエラーとして見せない（4.4 節）。無効化のエラーは、既存のエラーコードの仕組みで見せる。

## 9. 既定のメモリ

- 「自動」のメモリ値は、現在は固定値（`launcher.rs` の `AUTO_MEMORY_MB`）である。これを、全体設定で変えられるようにする。
- 保存形式は変えない。インスタンスの `memory_mode = auto` はそのまま残し、画面の表記だけを「自動」から「全体設定に従う」に変える。DB の移行はしない。
- 設定画面に、既定のメモリを 1 つ置く。値の範囲と入力の単位は、インスタンスの手動設定と同じ検証を使う（実装時に既存の検証に合わせる）。初期値は現在の `AUTO_MEMORY_MB` と同じにする。設定が保存されていないときは、この初期値を使う（既存の利用者の移行は要らない。実装者の判断で決めた方針）。画面の表記の変更は、メモリの選択肢の「自動」だけを「全体設定に従う」に置き換える。Java の選択肢の「自動」は、別の設定なので変えない（現在は両方が同じ文言を共有している）。
- 設定を変えると、「全体設定に従う」のインスタンスすべてに、次の起動から効く。手動のインスタンスには効かない。
- 物理メモリや MOD の数から値を決める処理は作らない。利用者の実績では、8 GB 付近が妥当で、16〜24 GB は多すぎた。上限を超える値を設定画面で防ぐかは、手動設定の検証に任せる（独自の上限は足さない）。

## 10. テストと実機確認

- 診断：ローダーごとの合成サンプル（ログとクラッシュレポート）で、各理由のコードが取り出せること。手がかりのない落ち方で「候補なし」になること。複数の候補が並び順どおりに出ること。MOD ID から jar への対応。
- 無効化：選んだものだけが `.disabled` になること。一部の失敗で残りが無効化されること。
- 既定メモリ：設定の値が「全体設定に従う」のインスタンスの `-Xmx` に反映され、手動のインスタンスには反映されないこと。
- 実機確認（利用者が行う）：依存が足りない MOD を入れて起動し、落ちたときに、その MOD が一覧に出ること。Mixin や読み込みの失敗が起きる MOD でも同じことを確かめる。実機で確かめるまで、各ローダーの書式は未確認として扱う。

## 11. 実装者に任せること

- 診断の呼び出し方（6 節）。
- 各ローダーのエラーの書式の調査と、調査資料の作成。
- スタックトレースのクラスから MOD を探す方法の詳細（jar のクラス一覧を読む費用が大きければ、キャッシュまたは確度が低いままの簡易な方法にしてよい）。
- ダイアログの見た目。既存のダイアログに合わせる。
