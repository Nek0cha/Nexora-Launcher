# フェーズ 7：`.mrpack` のインポートとエクスポート 設計

全体設計（`2026-10-15-nexora-architecture-design.md`）の 9.5 節（`.mrpack`）と 13 章を、実装できる大きさに切り分けた spec である。食い違う場合は、この文書を優先する。形式の仕様と防御策の詳細は `docs/research/04-content-providers.md` の 2 章にある。

## 1. 目的と方針

- Modrinth のモッドパック（`.mrpack`）から、ワンステップで遊べるインスタンスを作れるようにする。
- 自分のインスタンスを `.mrpack` として書き出し、他人に渡せるようにする。
- 利用者が見るのは「読み込む」と「書き出す」の 2 つの操作だけにする。ZIP の構造、ハッシュ、overrides の層などは見せない（画面に説明文を足さず、配置と形で伝える）。
- 失敗したときに、遊べない中途半端なインスタンスを残さない。

## 2. 範囲

### 2.1 含めるもの

- `.mrpack`（`formatVersion` 1）から**新しいインスタンスを作る**インポート。
- 既存インスタンスからのエクスポート。
- インポートしたファイルの Modrinth 上の情報は、既存のスキャンと識別（フェーズ 5）に任せて記録する。

### 2.2 含めないもの

- 既存のインスタンスへの `.mrpack` の追加（上書き・マージ）。
- Modrinth 上のモッドパックの検索と、URL からのインストール。ファイルを渡されたときのインポートだけを扱う。
- CurseForge の ZIP 形式（`manifest.json`）。フェーズ 8 以降。
- パックの更新（新しい `versionId` への差し替え）。
- 環境レシピ（フェーズ 9）。

## 3. インポート

### 3.1 入口

1. ホーム画面の「新規作成」の隣に「`.mrpack` を読み込む」ボタンを置く。押すとファイル選択を開く。
2. ウィンドウへ `.mrpack` をドロップしても同じダイアログが開く（ドラッグ＆ドロップはこれまでの画面と揃える）。

どちらも、まず**確認ダイアログ**を出す。内容は、パックの名前、Minecraft のバージョン、ローダーとそのバージョン、ファイル数、名前の入力欄（既定はパックの名前）。取り込む操作は 1 つのボタンだけにする。マニフェストを読めなかった・非対応だった場合は、このダイアログに理由を出して取り込めなくする。

### 3.2 受け入れる条件

次のいずれかに当てはまる場合は、**インスタンスを作らずに**エラーにする。

- `modrinth.index.json` が無い、または JSON として読めない。`formatVersion` が 1 でない。`game` が `minecraft` でない。
- `dependencies` に `minecraft` が無い。ローダーのキー（`fabric-loader`、`quilt-loader`、`forge`、`neoforge`）が 2 つ以上ある。
- 未知のキーが `dependencies` にある。
- 示されたローダーとバージョンの組み合わせを、Nexora の導入処理が扱えない（フェーズ 5 の対応範囲外）。
- `files[]` の必須項目（`path`、`hashes.sha1`、`hashes.sha512`、`downloads`、`fileSize`）が欠けている。
- 3.4 節の安全性の検査に違反するパスがある。

ローダーのキーが無いパックは Vanilla のインスタンスにする。

### 3.3 処理の順序

1 つのタスク（進捗付き）として次の順に進める。

1. ZIP を開き、マニフェストと全エントリーの名前を検査する（3.4 節）。
2. インスタンスを作成する。既存の `create_instance` と同じ導入処理（Vanilla、ローダー、Java）を使う。
3. `files[]` のうち、実行環境に必要なものをステージング用の一時ディレクトリへダウンロードし、検証する。
4. 検証が済んだものを、インスタンスの `.minecraft` 相当の場所の `path` へ移す。
5. `overrides/` を展開し、続けて `client-overrides/` を展開する（同名なら後者で上書き）。`server-overrides/` は使わない。
6. 既存のコンテンツのスキャンと識別を走らせ、`instance_contents` を整える。
7. 完了。インスタンスは通常どおり起動できる状態（`ready`）になる。

どこかで失敗したら、作成したインスタンスとステージングを**削除して**、失敗の理由を `FailureNotice` の形で示す（再試行は、利用者がもう一度ファイルを選ぶ）。キャンセルも同じ扱いにする。

### 3.4 安全性

調査 2 章の「Proposed Nexora import defenses」を採る。実装で確実に守ることを次に挙げる。

- 全パス（`files[].path` と、すべての overrides 層の ZIP エントリー）を検査し、次のものは拒否する：絶対パス、ドライブ指定（`C:foo` を含む）、UNC・デバイスパス、`..` を含む成分（`/` と `\` の両方で）、Windows の代替データストリーム（`:`）、予約デバイス名、末尾が `.` または空白の成分、大文字小文字を畳むと衝突するパス。
- 展開先は、コンポーネント単位で、ステージングのルートの下に収まることを確認する（文字列の前方一致で判定しない）。シンボリックリンク・ハードリンクのエントリーは拒否する。
- 上限：マニフェスト 5 MiB、エントリー数 50,000、展開後の合計 4 GiB、圧縮率 200 倍、ダウンロード 1 ファイル 512 MiB（マニフェストの `fileSize` を信用せず、受信したバイト数でも打ち切る）。これらは builder が実パックで確かめて調整してよい。
- ダウンロードは HTTPS のみ。ホストは `cdn.modrinth.com`、`github.com`、`raw.githubusercontent.com`、`gitlab.com` を完全一致で許可し、リダイレクトは最大 3 回、各リダイレクト先も許可リストで検査する。GitHub と GitLab が返す配信先のホスト（資産ホスト）は builder が実際に確かめて許可リストに加える。ループバック・プライベート・リンクローカルのアドレス、認証情報つき URL、別ポートへの切り替えは拒否する。`downloads` が複数あれば順に試す。
- ダウンロードしたバイト列は、`sha1` と `sha512` の両方、およびサイズが一致して初めて採用する。overrides は、ダウンロード分を置いた**後**に展開するので、overrides が同じパスを上書きしてよい（その場合の最終的な出所は overrides とする）。
- パックに含まれるスクリプトを実行しない。

### 3.5 環境の扱い

- `files[].env.client` が `unsupported` のファイルは取り込まない。`required` と `optional` はどちらも取り込む（`optional` も有効の状態）。`env` が無いファイルは `required` と見なす。
- 「`optional` を選ばせる」画面は作らない。取り込んだ後にコンテンツタブで無効にできる。

## 4. エクスポート

### 4.1 入口と操作

インスタンス詳細のヘッダーのメニューに「`.mrpack` として書き出す」を置く。押すとダイアログが開く。

| 部分 | 内容 |
|---|---|
| 版 | パックの版の文字列（`versionId`）。既定は `1.0.0` |
| config を含める | チェックボックス。既定はオン。`config/` 配下を overrides に入れる |
| 特定できなかったファイル | Modrinth で特定できず overrides に入るファイルの一覧（0 件なら出さない）。1 件でもあれば、配布のライセンスを確認する旨の警告を出し、確認のチェックを入れるまで書き出せない |

書き出し先はファイル保存ダイアログで選ぶ。実行中のインスタンスでも書き出せる（ファイルを読むだけ）。

### 4.2 書き出す内容

- `modrinth.index.json`：`formatVersion` 1、`game: "minecraft"`、`versionId`（入力値）、`name`（インスタンス名）、`dependencies`（`minecraft` とローダーのバージョン。Vanilla はローダー無し）。
- `files[]`：`mods`、`resourcepacks`、`shaderpacks` の**有効な**コンテンツのうち、Modrinth のバージョンを特定できたものを参照として書く。URL とハッシュは Modrinth API（ハッシュからバージョンを引く一括の呼び出し）で得る。`env` は `client_side`・`server_side` から作る。
- 特定できなかった有効なコンテンツは、`overrides/<元の場所>` に実ファイルとして入れる。
- 無効（`.disabled`）のコンテンツは書き出さない。
- overrides には、`config/`（4.1 の選択による）を入れる。`options.txt`、ワールド、スクリーンショット、ログ、アカウント情報、キャッシュは**書き出さない**（個人情報と容量のため）。
- Modrinth に接続できないときは、特定できなかったものの扱いが決められないため、書き出しを無効にして理由を示す。

### 4.3 書き出しの失敗

一時ファイルに書き、完了後に指定の場所へ移す。途中で失敗したら一時ファイルを消し、指定の場所に不完全なファイルを残さない。

## 5. 画面とエラー

- 失敗の表示は既存の `FailureNotice` に合わせる。
- 進捗はタスクの進捗として出す（既存のタスク UI）。
- 画面に説明文を足さず、配置・形・アイコンで伝える（利用者の好み）。

## 6. テスト

- パスの検査：拒否すべきパスの一覧を網羅したテーブルテスト（`..`、`\`、ドライブ、UNC、ADS、予約名、末尾 `.`、大小文字衝突、シンボリックリンク）。
- ZIP の上限（エントリー数、合計サイズ、圧縮率）を、小さな上限に差し替えて検査する。
- マニフェストの受け入れ条件の各分岐（3.2 節）。
- ダウンロード：HTTP をモックし、ハッシュ不一致、サイズ超過、許可外ホスト、リダイレクトの上限と許可外への飛び先、複数 `downloads` のフォールバックを検査する。
- 層の順序：`files` → `overrides` → `client-overrides` の上書き順。
- 失敗時にインスタンスとステージングが消えること。
- エクスポート：特定できたもの・できなかったもの・無効なものの振り分け、除外対象、書き出した `.mrpack` を自分のインポートで読み直せること（往復テスト）。
- 画面：インポートダイアログ（正常、非対応）、エクスポートダイアログ（警告のチェックで書き出しが有効になる）。スクリーンショットを PR に添付する。
- 実機で確認すること：Modrinth の実際のパック（Fabric と Forge）の取り込みと起動、書き出したパックを Modrinth App（または別の環境）で読み込めること。

## 7. 私が決めたこと

ユーザーから「任せる」と言われたため、次は私の判断である。読んで違えば言ってほしい。

- インポートは「新しいインスタンスを作る」だけにした（既存への追加はしない）。
- `optional` のファイルは選ばせず、すべて有効で入れる。
- 失敗やキャンセルでは、インスタンスを残さず消す。
- エクスポートは無効なコンテンツを含めない。`options.txt` とワールドは含めない。`config/` は既定で含める。
- Modrinth で特定できなかったファイルは、警告に同意した場合のみ overrides へ入れる。
- 上限の数値と、GitHub・GitLab の配信先ホストは暫定で、実装時に実物で確かめる。
- Forge のバージョン文字列（`.mrpack` の形式と Nexora の保存形式の対応、旧形式の Forge を含む）は、builder が既存のローダー導入の実装と突き合わせて決める。

## 8. 実装前の確認で補ったこと

実装担当の視点で読んだ確認（2026-10-31）への答えである。いずれも私の判断で、利用者の判断を要するものはなかった。

- **識別の仕組み**：既存の `content::identify::identify` と `content::modrinth::versions_by_hash` を使う。エクスポート時の一括照会も `versions_by_hash` を再利用し、新しい API 呼び出しは作らない。`instance_contents` に Modrinth の ID や `client_side`・`server_side` が入っている前提は、エクスポート側では**信用せず**、書き出しの時点で一度ハッシュから引き直す（古い記録や未識別のファイルに強くするため）。
- **インポート直後の識別**：手順 6 の識別は失敗してもインポートを失敗にしない。オフラインなどで識別できなかったファイルは、通常の未識別（`local`）として残り、コンテンツタブを開いたときの既存の再識別に任せる。
- **ローダーの対応範囲**：Fabric、Quilt、Forge（旧形式を含む）、NeoForge の 4 種はフェーズ 5 で導入できる。確認ダイアログの時点の拒否判定のため、`.mrpack` のローダーとバージョンが導入処理の一覧にあるかを事前に調べる関数を core に足す。
- **失敗時の削除**：既存の `instance::delete`（インスタンスのディレクトリ、DB の行、ネイティブ・引数ファイル・ログの残りを消す）を使う。Java と Vanilla、ローダーの共有キャッシュ（`shared/` 側）は消さない。導入途中（`installing`）のインスタンスを削除するときは、導入タスクを止めてから消す。
- **`env` の変換**：`client_side`・`server_side` の `required` / `optional` / `unsupported` をそのまま `env.client` / `env.server` に写す。値が無い（不明）場合は `env` を書かない。
- **ドロップの振り分け**：ウィンドウ全体のドロップは拡張子で振り分け、`.mrpack` はインポートのダイアログを開く。コンテンツタブなど、既存の受け口が先に処理する場所では、既存の挙動を変えない。

## 9. 実装後の差分

実装と、実在のパックでの確認（2026-10-31）で、この spec から変わったこと。

- **「読み込む」ボタンの場所**：ホームではなく、インスタンスの一覧の作成ボタンの隣（インスタンスが 0 件のときは空の状態の作成ボタンの隣）に置いた。ホームに作成ボタンがあるのは空のときだけで、通常の入口は一覧にあるため。
- **ファイル選択**：アプリに選択ダイアログの仕組みが無かったため、公式の `tauri-plugin-dialog` を足した（開く、保存の 2 つの権限だけ）。
- **許可ホスト**：`release-assets.githubusercontent.com` を足した。`github.com` のリリースのファイルは、実際にここへ 1 回リダイレクトされる（2026-10-31 に確認）。`objects.githubusercontent.com` も、従来の配信先として許可した。GitLab は実物で確かめておらず、`gitlab.com` 自身が返す場合だけを許す。
- **上限**：spec 3.4 の暫定値のまま変えていない。実在の 2 つのパック（Fabulously Optimized、約 170 KiB、48 ファイル。Cobblemon、約 96 MiB、77 ファイルと overrides 2,436 ファイル）は、どの上限にも当たらずに読めた。
- **書き出しの `env`**：インスタンスが実際に使っているファイルは、クライアントで `unsupported` と書かない（プロジェクトがクライアント非対応としていても `required` にする）。プロジェクトの値をそのまま写すと、実在のパックを往復したときに 48 件中 1 件が読み込み直しで入らなくなった。サーバー側の値は写す。片方だけ不明なときの `optional` は spec 8 章のとおり。
- **失敗の知らせ**：失敗したインポートはインスタンスごと消えるため、何も起きなかったように見える。そこで、読み込みのタスクが失敗で終わったときに、理由をトーストで知らせ、一覧を取り直す。
- **書き出し後の知らせ**：書き出せたら、短いトーストで知らせる。

### 実在のパックでの確認

- Fabulously Optimized（Fabric、Minecraft 26.3）を実際の通信で読み込み、約 33 秒で成功した。MOD 46 件とリソースパック 3 件が Modrinth で特定でき、書き出しの内訳は参照 48 件、特定できないもの 1 件（パックが同梱していた `Mod Menu Helper.zip`）だった。書き出したパックを読み直すと、ファイル数が元と同じ 48 件になった。
- 確かめられていないこと：Forge と NeoForge のパックの読み込み、旧形式の Forge、書き出したパックを Modrinth App など別のランチャーで開くこと、画面の見た目（スクリーンショット）。
